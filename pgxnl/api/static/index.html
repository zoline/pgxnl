방금 실행에 성공한 SQL을 유사 쿼리 탐색에 남깁니다. 실행을 거치지 않은 SQL은 등록할 수 없습니다 — 도는지 확인되지 않은 예제는 참고가 아니라 함정입니다. 등록 뒤 SQL 수집 화면에서 승인해야 탐색에 나옵니다.

수동 등록

실행이력/SQL 수집에서 발견되지 않은 관계를 직접 알고 있을 때 등록합니다. 등록 즉시 승인 상태로 반영됩니다. 위에서 고른 스키마로 등록하고, "(전체)"면 대상 DB 카탈로그에서 테이블의 스키마를 찾습니다. 승인된 관계는 그 스키마의 질의에 조인 경로로 전달됩니다(재색인 후).

승인된 JOIN

승인된 관계는 그 스키마 질의의 스키마 정보에 조인 경로로 들어갑니다. 승인·해제 모두 해당 스키마를 재색인해야 질의에 반영됩니다(캐시 → 스키마 벡터). 해제하면 대기 후보로 돌아가고 삭제되지 않습니다.

Design Lab

스키마의 정규형을 검토해 자연어 질의가 구조적으로 모호해지는 지점을 찾습니다. 같은 개념이 여러 테이블에 사본으로 있고 값까지 갈리면, 모델이 정답 논리를 알아도 다른 사본을 고르면 틀립니다. 검토는 결정론적 분석이며(LLM 미사용) 읽기 전용 SQL만 씁니다 — 데이터를 훑으므로 큰 스키마에서는 시간이 걸립니다.

진행 로그 · 프롬프트 전문

이행 종속·중복 개념 항목을 3NF로 바꾸는 제안을 하나씩 따라갑니다 — 이유, 적용 전/후 모습, 그 단계의 DDL. 보기 전용이며 DDL을 실행하지 않습니다. 반복 그룹·혼합 단위는 사람 판단이 필요해 대상이 아닙니다(② LLM 의견 참고). ② 탭에서 "발견 항목 기반" 의견을 받으면 단계마다 양쪽 의견(코드 + LLM 동의)인지 코드 단독인지 표시됩니다.

SQL 규칙

SQL 생성 전·중·후에 적용되는 규칙입니다. 만들어진 SQL만 보고 판정되는 것은 생성 뒤에 두세요.

도움말 — 규칙 종류와 고르는 기준

규칙은 어디서 적용되는가로 갈립니다. 같은 지식이라도 자리가 달라지면 비용과 사정권이 달라지므로, 새 규칙을 만들 때 가장 먼저 정할 것이 종류입니다.
기준 — "만들어진 SQL만 보고 판정되는가?" 된다면 생성 뒤에 둡니다. 예외를 프롬프트에 두면 모든 질의에서 저울질이 일어나 무관한 문항이 깨집니다 (2026-09-10 실측: 한 문항용 예시를 프롬프트에 넣자 그 문항은 얻었지만 무관한 세 문항을 잃었고, 같은 지식을 생성 뒤로 옮기자 손실이 0이었습니다).

종류적용 시점판정 주체프롬프트 비용
generation_constraint생성 전 (프롬프트)모델항상 지불
few_shot생성 전 (프롬프트)모델항상 지불
advisory_guardReAct 루프 안코드발동 시만
canonical_rewrite생성 후LLM → 실패 시 파서없음
canonicalization생성 후 (마지막)파서없음

generation_constraint — 프롬프트에 번호 매긴 명령문으로 들어갑니다. 문장이 늘수록 모델이 일부를 무시하고, 무관한 문항이 흔들립니다. 판정 가능한 것은 아래 두 종류로 내리는 편이 낫습니다.
few_shot — "항상 A 해라/하지 마라"가 잘 안 먹히는 경계 판단(예: 언제 컬럼을 추가해도 되는지)에 씁니다. 질문+좋은 SQL(+나쁜 SQL 대비)을 통째로 보여줍니다. 설명에 일반 지시문("~할 때는 항상 ~하라")을 쓰면 few_shot의 탈을 쓴 전역 규칙이 되어 좁은 적용이라는 장점이 사라집니다.
canonicalization — 파스 트리를 보고 SQL을 고칩니다. 결정론적이고 프롬프트를 건드리지 않아 가장 안전합니다. 새 변환을 늘리려면 코드(CanonRule)가 필요합니다.
canonical_rewrite — 자리는 위와 같고 판정 주체만 다릅니다. 고치기 전 → 고친 뒤 예시 쌍을 보여주면 LLM이 적용합니다. 파서로 판정할 수 있으면 위쪽을 쓰세요 — 확실한 것을 불확실하게 만들 이유가 없습니다. 이 종류는 파서로는 못 정하는데 SQL만 보면 사람은 아는 변환을 위한 것이고, 코드 없이 늘릴 수 있다는 게 존재 이유입니다.
  · LLM이 수용되는 변경을 못 내면(시간 초과·문법 오류·값 변조·아예 무변경) 대신 수행할 파서 규칙이 확정합니다. 지정하지 않으면 원본을 그대로 둡니다.
  · 재작성은 경계가 없으므로 코드가 검증합니다 — 참조 테이블과 WHERE·HAVING·조인 조건의 값이 그대로여야 하고, 바꿀 수 있는 것은 SELECT 목록과 컬럼 순서뿐입니다. 어긋나면 재작성을 버립니다.
  · 언제 시도할지(정규식)를 비우면 모든 SQL에 LLM 호출이 붙습니다. 걸릴 때만 부르도록 좁히세요.

advisory_guard는 생성된 SQL을 보고 관찰을 ReAct 루프에 돌려줍니다 — 코드가 SQL을 고치지 않고, 모델이 다시 판단합니다. kind로 검사를 고릅니다.
  · null_ratio — 질문에 valid 같은 낱말이 있는데 SELECT에 값의 99%가 NULL인 컬럼이 들어 있으면 그 사실을 알려줍니다. 발동 낱말이 비면 동작하지 않습니다. 영문은 낱말 경계로 봅니다(valid가 invalid/validity에 걸리지 않습니다). 판정은 ANALYZE 시점의 통계에 의존합니다.
  · ambiguous_column — 필터 값이 다른 컬럼에도 흔한지. 어느 쪽이 맞는지는 판정하지 않고 사실만 돌려줍니다.
  · redundant_join — 붙인 테이블이 조건에 한 번도 안 쓰였는지. 조인을 코드가 지우지는 않습니다 — INNER JOIN은 매칭 없는 행을 걸러내므로 "안 쓰는 조인"처럼 보여도 실제로는 필터일 수 있습니다.
  · column_rationale — SELECT 항목이 질문 어느 구절에서 왔는지 LLM에게 대조시킵니다. 디버그 표시용이고 판정에는 쓰지 않습니다.
  · single_column — 요구하지 않은 컬럼 검사. 30문항 A/B에서 EX 기여가 0이고 오탐 1건이 정답 1건을 잃어 꺼 두기를 권장합니다.
조언형 가드는 질의당 한 번만 발동합니다. 같은 말을 반복하면 ReAct가 반복 횟수를 소진해 SQL을 아예 못 냅니다.
목록 아래 "내장 가드" 행들은 코드에 박혀 있어 끄고 켤 수 없습니다. 실행하면 반드시 실패하는 SQL을 되돌리는 검사들이라(참조 컬럼 부재, 서브쿼리 별칭 스코프, 스칼라 서브쿼리 컬럼 개수, WHERE의 윈도우 함수) 켜야 할 이유가 "안 켜면 SQL이 죽는다"로 고정돼 있습니다. 이 중 셋은 조언형과 달리 고칠 때까지 매번 되돌립니다.

질문 표현을 컬럼에 잇고 컬럼 의미·PII를 적습니다. SQL 생성과 질문 보강에 쓰입니다.

도움말 — 적용 범위, 스키마 지정, 수집 방식

컬럼 의미를 설명하고 PII 여부를 표시합니다. describe_table 도구 결과에 자동 병합되고, PII 컬럼이 있는 테이블을 참조하는 SQL은 검증 단계에서 차단됩니다. 스키마를 비워두면 해당 대상 DB의 모든 스키마에 적용됩니다(BIRD처럼 스키마가 여러 개면 동명 테이블에 전부 적용되니 주의 — 특정 스키마에만 적용하려면 스키마명을 지정하세요).

적용 범위: "SQL 생성 전용"은 schema_context에만(질문 보강 단계는 스키마를 몰라 못 씀), "질문 보강 전용"은 모호성 판단/재작성 참고에만, "양쪽 모두"는 둘 다에 쓰입니다. 용어가 많아지면 "질문 보강 전용/양쪽 모두"만 늘어도 그 단계 프롬프트가 커지니, 코드값 표처럼 큰 항목은 "SQL 생성 전용"으로 등록하는 걸 권장합니다.

스키마 구조(사본 컬럼·열거값·이행 종속·코드 컬럼)에서 용어집 후보를 뽑습니다. 같은 분석의 전체 결과는 Design Lab 화면에서 볼 수 있습니다. 등록하지는 않습니다 — 아래 목록에서 고른 것만 들어갑니다. 같은 컬럼에 이미 항목이 있으면 기존으로 표시되고, 기본은 건너뛰기입니다 (사람이 쓴 지식을 모르고 덮어쓰지 않도록).
