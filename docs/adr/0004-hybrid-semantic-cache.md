# ADR-0004: 시맨틱 캐시를 pg_trgm + 임베딩 하이브리드로 전환하고 캐시 히트에도 검증 재수행

- **상태**: Accepted
- **날짜**: 2026-08

## Context

기존 pgxrsa의 `pgxrsa_cache`는 `pg_trgm` 유사도(threshold 0.85)만으로 "시맨틱
캐시"를 구현하고 있었다. 그러나 `pg_trgm`은 문자 n-gram 기반 **어휘적** 유사도이지
**의미적** 유사도가 아니다 — 표현이 다르지만 의미가 같은 질문("이번달 매출" vs
"이달 매출")을 못 잡거나, 반대로 표현은 비슷하지만 의미가 다른 질문을 잘못 캐시
히트시킬 위험이 있다.

또한 기존 질의 흐름도상, 캐시 히트 시 바로 캐시된 답변을 반환하는 것으로 보였다.
이 경우 캐시를 만든 사용자와 조회하는 사용자의 권한이 다르면(RLS/CLS 등), 권한이
없는 사용자가 캐시된 결과를 그대로 받아보는 보안 문제가 발생할 수 있다.

pgxnl은 이미 Schema RAG(§5.4)용 BGE-M3 임베딩 인프라를 갖추고 있어, 캐시 조회에도
같은 임베딩을 재사용할 수 있는 여건이 된다.

## Decision

1. **하이브리드 캐시 조회**: 1차로 `pg_trgm`(threshold 0.85)으로 저비용 스크리닝하고,
   미스면 2차로 임베딩 코사인 유사도(threshold 0.90)로 의미 기반 재조회한다. 2차는
   `PGXNL_CACHE_EMBEDDING_ENABLED`로 개별 on/off 가능하며 기본값은 `false`다.
2. **캐시에는 SQL 템플릿만 저장**한다. 실행 결과 원본은 저장하지 않는다 — 대상
   테이블의 데이터 자체가 계속 바뀌기 때문이다.
3. **캐시 히트는 SQL "생성" 단계만 건너뛴다.** 검증·거버넌스 계층(§5.9, ADR-0006)은
   캐시 히트 여부와 무관하게 항상 재실행한다. 이 책임은 `Orchestrator.analyze()`에
   명시적으로 고정한다.

## Consequences

- **장점**: 이름과 실제 동작(의미 기반 매칭)이 일치하게 된다. 표현이 다른 질문도
  캐시를 재사용할 수 있어 히트율 개선을 기대할 수 있다. 무엇보다, 캐시 히트 시
  권한 검사를 생략하던 잠재적 보안 공백을 제거한다.
- **트레이드오프**: 캐시 조회마다 임베딩 API 호출이 추가될 수 있어(2차 조회 시)
  지연시간이 늘 수 있다 — 1차 스크리닝을 저비용으로 유지해 대부분의 케이스에서는
  2차까지 가지 않도록 완화한다. 임베딩 threshold(0.90)는 초기값이며 오탐/누락 사례를
  모니터링하며 조정이 필요하다.
- **구현 우선순위**: design 문서 로드맵에서 "캐시 히트 시 권한 재검사 강제"를
  2순위로 앞당겼다 — 다른 신규 기능보다 먼저 확인/수정해야 할 보안 관련 항목이기
  때문이다.
