# ADR-0008: 스키마를 경량 검색용 표현과 M-Schema 전체 표현으로 이중화

- **상태**: Accepted
- **날짜**: 2026-08

## Context

기존 pgxrsa의 `SchemaVectorIndex`는 테이블 DDL 전체를 하나의 문서(`doc`)로
임베딩하는 구조였다. 값 예시가 잔뜩 포함된 텍스트를 그대로 임베딩하면, 벡터가
"이 테이블이 무엇에 관한 것인가"라는 의미보다 "어떤 값들이 들어있는가"라는 표면적
특징에 쏠리는 문제가 있다. BIRD 벤치마크 실증 실험(financial/california_schools
DB)에서도 값 예시가 섞인 청크가 검색 정밀도를 떨어뜨리는 사례를 여러 번 확인했다.

## Decision

테이블을 두 가지 표현으로 이중화한다 (`pgxnl/agent/mschema.py`).

- **경량 표현(`to_light_doc`)**: 테이블/컬럼명 + 코멘트만 포함, 값 예시 제외.
  **임베딩 검색 전용**이며 `pgxnl_schema_vectors.doc`/`embedding`에 저장된다.
- **M-Schema 전체(`to_mschema`)**: 값 예시(중복 제거, 최대 3개, 각 50자 제한) +
  PK/FK 정보를 포함하는 XiYan-SQL 계열 반구조화 표현. **검색된 테이블에 한해서만**
  조립되어 SQL 생성 프롬프트에 전달되며 `pgxnl_schema_vectors.mschema`(JSONB)에
  저장된다.

검색은 경량 표현으로, 프롬프트 조립은 M-Schema 전체로 — 역할을 명확히 분리한다.

## Consequences

- **장점**: 임베딩은 "무엇에 관한 테이블인지" 찾는 데만 집중해 검색 정밀도가
  개선될 것으로 기대한다. SQL 생성 프롬프트는 필요한 만큼 풍부한 정보(값 예시,
  FK)를 여전히 받는다. 임베딩 모델을 교체하거나 검색 알고리즘을 튜닝해도 M-Schema
  조립 로직은 건드릴 필요가 없다(관심사 분리).
- **트레이드오프**: 테이블 하나당 두 가지 표현을 유지·갱신해야 하므로 인덱싱
  로직이 약간 더 복잡해진다. `pgxnl_schema_vectors` 테이블에 `mschema` 컬럼이
  추가로 필요하다.
- **관련 결정**: PK/FK 정보는 M-Schema 텍스트에 섞기보다 `[Foreign Keys]` 별도
  섹션으로 명시한다 — 조인 경로 판단은 유사도 검색보다 그래프 순회/명시적 참조가
  더 적합하기 때문이다.
