# ADR-0005: 모든 부가 기능을 "필수 경로 + 보조 Provider"로 분리

- **상태**: Accepted
- **날짜**: 2026-08

## Context

오늘 설계 논의 과정에서 질문 보강, 스키마 링킹 강화(임베딩/FK그래프/값링킹),
문서 지식 레이어, SQL Canonicalization, 검증 계층, 시맨틱 캐시 등 다수의 컴포넌트가
추가됐다. 이 모든 컴포넌트가 시스템 동작의 전제조건이 되면, 다음 문제가 생긴다.

- 새 대상 DB를 온보딩할 때 모든 컴포넌트를 처음부터 다 갖춰야 시작할 수 있다.
- 한 컴포넌트(예: 임베딩 서버)에 장애가 나면 시스템 전체가 멈춘다.
- 컴포넌트 간 결합도가 높아져 개별 교체·튜닝이 어려워진다.

## Decision

- **최소 동작 경로**를 정의한다: 사용자 질문 → 스키마 정보 확보(최소 DDL) → LLM
  SQL 생성 → 실행 → 답변. 이 경로는 다른 어떤 컴포넌트가 없어도 항상 성립해야 한다.
- 모든 부가 컴포넌트는 동일한 인터페이스(`retrieve() -> list | None` 또는 이에
  준하는 형태)를 갖는 **Provider**로 구현한다. 설정이 없으면 빈 결과/`None`을
  반환하고, 호출부는 "있으면 A, 없으면 B" 식의 분기를 코드에 흩뿌리지 않는다.
- 각 Provider는 대응하는 환경변수로 개별 on/off 가능해야 하며, **기본값은 모두
  `false`**로 시작한다 (예외: `PGXNL_CANONICALIZATION_ENABLED`,
  `PGXNL_AUDIT_LOG_ENABLED`는 보안/일관성에 직결되어 기본 `true`).

## Consequences

- **장점**: 점진적 온보딩이 가능하다 — 새 DB는 필수 경로만으로 먼저 서비스하고,
  이후 메타데이터/문서/규칙을 채워가며 정확도를 계단식으로 올릴 수 있다. 장애
  격리가 자연스럽다 — 문서 지식 레이어의 벡터 DB가 죽어도 `DocumentStore.search()`가
  빈 리스트를 반환하면 나머지 파이프라인은 그대로 동작한다.
- **트레이드오프**: 모든 컴포넌트에 "없을 때의 폴백 경로"를 설계하고 테스트해야
  하는 추가 비용이 있다. Provider 인터페이스가 너무 일반화되면 각 컴포넌트의
  고유한 파라미터(top_k, threshold 등)를 넘기기 위한 보일러플레이트가 늘 수 있다.
- **예외**: §5.9(검증 계층)는 이 원칙의 예외로 취급한다 — "없어도 동작"하지만
  "없으면 안전하지 않은" 컴포넌트라, 필수/보조 이분법과 별개로 "프로덕션 필수"로
  분류한다 (ADR-0006 참고).
