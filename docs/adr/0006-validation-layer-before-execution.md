# ADR-0006: SQL 실행 전에 코드 전용 검증·거버넌스 계층을 강제

- **상태**: Accepted
- **날짜**: 2026-08
- **관련**: ADR-0004, ADR-0005

## Context

기존 pgxrsa는 read-only 가드(AST 파싱으로 DML/DDL 차단 + DB 세션
`SET TRANSACTION READ ONLY`)만 갖추고 있었다. 이는 "쓰기 방지"는 되지만, 다음은
다루지 못한다.

- 존재하지 않는 테이블/컬럼 참조 (카탈로그 바인딩 미검증)
- 사용자 권한 범위를 벗어난 행/컬럼 접근 (RLS/CLS 미연동)
- 민감 필드(PII) 노출
- 과도한 비용의 쿼리(대형 테이블 전체 스캔 등)로 인한 성능 저하
- 판정 근거를 남기지 않아 사후 감사 불가능

또한 ADR-0004에서 다룬 것처럼, 캐시 히트 경로가 이 계층을 우회할 위험도 있었다.

## Decision

`generate_sql` 도구에서 `execute_sql`을 분리하고, 둘 사이에 **검증·거버넌스
계층**(`pgxnl/agent/validation.py`)을 강제한다. 이 계층은 다음을 순차 수행한다.

1. SQL 파싱 (ANTLR, ADR-0002)
2. read-only 판정 (DML/DDL 즉시 거부)
3. 카탈로그 바인딩 (존재하지 않는 테이블/컬럼 검증)
4. 권한 검사 (RLS 연동 또는 애플리케이션 레벨)
5. 민감 필드 탐지 (`GlossaryStore`의 PII 태그 활용)
6. 비용 추정 (`EXPLAIN (FORMAT JSON)`)
7. 판정(허용/거부/수정요청) + 감사 로그 기록 (`pgxnl_audit_log`)

이 계층 전체는 **LLM 호출이 없는 순수 코드**로 구현한다 (§2.2 원칙) — 검증 로직
자체가 LLM에 의존하면 검증의 신뢰성이 훼손되기 때문이다.

캐시 히트로 SQL 생성을 건너뛴 경우에도, 이 계층은 **반드시 재통과**해야 한다
(ADR-0004).

## Consequences

- **장점**: LLM이 잘못된/악의적인 SQL을 생성하더라도(질문 자체에 prompt injection이
  섞여 있는 경우 포함) 실행 전 마지막 방어선이 확보된다. 감사 로그로 거부된 요청도
  포함해 재현 가능한 기록이 남는다.
- **트레이드오프**: 모든 요청에 `EXPLAIN` 호출이 추가되어 지연시간이 늘어난다.
  RLS 연동은 대상 DB에 정책(`CREATE POLICY`)이 미리 구성되어 있어야 하므로,
  RLS가 없는 환경에서는 애플리케이션 레벨 권한 검사로 대체해야 한다(신뢰도가
  DB 레벨보다 낮음을 인지하고 사용).
- **분류**: 이 계층은 ADR-0005의 필수/보조 이분법과 별개로 **"프로덕션 필수"**로
  분류한다. 없어도 시스템은 "동작"하지만, 엔터프라이즈 배포가 불가능한 수준의
  리스크를 안게 되기 때문이다.
- **재시도 종류 구분**: "수정요청"(권한/정책 위반)은 §generate_sql의 문법/실행
  오류 기반 자기수정 루프와 **다른 종류의 재시도**다. LLM에게 주는 피드백 내용이
  달라야 한다(예: "이 컬럼은 접근 권한이 없으니 다른 방식으로 답하라").
