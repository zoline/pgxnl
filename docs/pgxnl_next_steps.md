## 2. 446 — 답이 둘인 문항. 아무것도 고치지 않는다 (2026-09-14 결론)

한때 evidence를 보완해 gold와 8,574행 완전 일치를 만들었지만 **철회했다.** gold에
결함이 없고 답이 둘(813행/8,574행)이라 EX를 올리려고 질문을 gold 쪽으로 민 것이었다.

그 뒤 "질문만으로 답이 정해지므로 우리 쪽 읽기 실패"라고 적었는데 **그것도 틀렸다.**
근거 세 개를 하나씩 검증한 결과:

| 근거 | 판정 |
|---|---|
| `"if there is any"` 가 LEFT JOIN을 암시 | **✗** 문법적으로 `communication number`에 붙는다. INNER 쪽(813행)에도 phone NULL이 33건(4.1%)이라 그 문구가 무의미하지 않다 |
| `"names along with the score"` 가 조인을 강제 | **✗** `satscores` 에 `sname`·`avgscrwrite` 가 **둘 다** 있다. 조인을 강제하는 것은 전화번호와 날짜 조건(둘 다 `schools`)이다 |
| 모든 필터가 `schools` 속성 | **△** 약한 정황. 조건 출처는 `schools` 지만 "점수를 묻는다"는 `satscores` 쪽을 시사한다 |

오히려 `satscores` 에 이름과 점수가 함께 있다는 사실은 **모델의 읽기를 지지한다** —
pred는 두 값을 한 테이블에서 가져오고 필요한 것만 조인한다. gold는 `satscores.sname` 을
쓸 수 있는데도 `schools.School` 을 쓰는데, **그 선택이 있어야 LEFT JOIN이 의미를 갖는다**
(이름을 `satscores` 에서 가져오면 매칭 없는 행의 이름이 NULL이라 무의미해진다 —
측정: 7,848행 불일치). 즉 gold는 "모든 학교를 나열한다"는 결론을 먼저 정하고 컬럼을
그에 맞췄다. 질문의 표현이 그 결론을 요구하지는 않는다.

**결론: 데이터도 모델도 손대지 않는다.** 답이 둘인 문항으로 남긴다. EX 상한은 29다.

## 4. 가드 분류 정리

지금 루프에서 도는 검사는 일곱인데 규칙 화면에 보이는 건 셋이다.

```
missing_column    alias_scope    scalar_subquery    window_misuse   ← 코드에 박혀 있음
column_rationale  redundant_join  single_column(비활성)             ← question_guard
null 비율                                                           ← stats_guard
```

분류 축도 종류마다 다르다 — `generation_constraint↔few_shot`은 형식,
`canonicalization↔canonical_rewrite`는 판정 주체, `stats_guard↔question_guard`는
근거. 셋째 축은 사용자에게 의미가 없다(둘 다 "루프에 조언을 돌려준다").

`advisory_guard` 하나로 합치고 `kind`로 구분한다:

```
advisory_guard  kind: missing_column | alias_scope | scalar_subquery | window_misuse
                      (실행하면 반드시 실패 — 항상 켜기 권장)
                kind: null_ratio (구 stats_guard — trigger, threshold)
                kind: redundant_join | column_rationale | single_column(꺼 두기 권장)
```

얻는 것: 화면 하나에서 도는 검사 전부가 보이고, 개별로 끄고 켜지며, 가드 단위로
값어치를 잴 수 있다. 마이그레이션이 딸린 구조 변경이라 기준선이 흔들리는 것을
피하려면 2·3 뒤에 둔다.

## 1-b. seq 467 — "valid"는 BIRD 관용어다 (2026-09-04)

467의 pred와 gold는 **필터가 완전히 같고**(둘 다 같은 학교 1건), 오직 `admemail3`
컬럼 하나가 더 있어서 틀린다. 그 값은 NULL이다.

```
GOLD  a.lucero@realjourney.org, j.hernandez@realjourney.org
PRED  a.lucero@realjourney.org, j.hernandez@realjourney.org, NULL
```

처음에는 "질문이 개수를 안 정했으니 gold가 임의로 2개를 택한 것"으로 봤는데 **틀렸다.**
`valid`는 이 데이터셋의 관용어이고 다른 문항에 정의가 있다:

```
seq 441 근거: "Valid charter number means the number is not null"  -> gold에 NOT ... IS NULL
seq 467 질문: "the valid e-mail addresses"  (근거에 정의 없음)     -> gold가 NULL인 3번을 제외
seq 474      "loan validity" — 전혀 다른 뜻(duration > 12)
```

**467은 gold 결함이 아니라 모델의 실제 오답이다.** 다만 `valid`의 정의가 *다른 문항의*
근거에 있어 추론 시점에는 보이지 않는다.

### 제안: 실행 결과로 판정하는 결정론적 교정 (2026-09-04 마지막 논의)

프롬프트 규칙 대신 **코드**로 처리할 수 있다:

> 질문에 `valid`가 있으면, 실행 결과에서 **전부 NULL인 SELECT 컬럼을 출력에서 제외**한다.

`valid = not null`을 컬럼 단위로 해석한 것이다. seq 467의 `admemail3`이 정확히 이
경우이고(결과 1행이 NULL), 제외하면 gold와 일치한다.

**안전성 검증 — 질문에 `valid`가 있는 2문항 모두 gold에 전부-NULL 컬럼이 없다:**

```
seq 467 [california_schools]  1행, gold 컬럼 [admemail1, admemail2]  전부-NULL: 없음
seq 474 [financial]           1행, gold 컬럼 [account_id]            전부-NULL: 없음
```

즉 이 교정은 **gold를 깨뜨리지 않는다**(오탐 0). seq 474의 "loan validity"는 뜻이
다르지만(duration > 12), gold 컬럼이 NULL이 아니라 아무것도 제외되지 않아 무해하다.

**구현 시 주의:**
- 결과가 0행이면 모든 컬럼이 공허하게 "전부 NULL"이 된다 -> **1행 이상일 때만** 적용
- 최소 1개 컬럼은 남겨야 한다
- 실행 후 판정이므로 SELECT를 재작성하고 **한 번 더 실행**해야 한다.
  `valid`가 있는 질문에만 걸리므로 비용은 500문항 중 2건이다.
- SELECT 재작성은 `Target_elContext`를 모아 남길 것만 이어 붙인다
  (`TokenStreamRewriter`, `CanonicalColumnRule`과 같은 방식)

### 더 나은 방향: 실행 시점이 아니라 스키마에 표현하기

실행 후 판정하는 대신 **Design Lab이 미리 찾아 mschema에 표시**할 수 있다.
반복 그룹 컬럼의 NULL 비율을 재보면 사실상 죽은 컬럼임이 드러난다:

```
schools 반복 그룹의 NULL 비율
  admemail1  34.0%      admemail2  97.6%
  admemail3  99.8%      admfname3  99.8%      <- 17,686행 중 약 35행만 값이 있다
```

`admemail3`은 **99.8%가 비어 있다.** 이런 컬럼을 SELECT에 넣으면 거의 항상 NULL
열이 하나 붙는다. mschema에 표시하면 모델이 애초에 고르지 않는다:

```
(admemail3, text, 99.8% NULL),
```

`copy of X` 표시(A-11)와 같은 자리이고, 같은 이유로 **블록 크기를 거의 안 바꾼다**.
실행을 두 번 하지 않아도 되고, `valid`라는 단어에 의존하지도 않는다 — 더 일반적이다.

다만 **PK 태그 2토큰이 EX를 2점 움직인 전례**가 있으므로(2026-09-03), 표시를 늘리는
것 자체가 무해하다고 가정하면 안 된다. 임계값(예: 95% 이상)과 대상 범위를 정하고
측정할 것.

### 배치는 JOIN 그래프를 따랐다

별도 메뉴(`용어 수집`)나 화면 안 탭도 후보였지만 둘 다 접었다.

- **별도 메뉴** — 수집·검토·확정이 한 흐름인데 화면이 갈리면 왔다 갔다 해야 하고
  "이미 등록된 것"과 대조가 안 된다. JOIN 후보만 따로 메뉴를 두는 것과 같은 어색함이다.
- **화면 안 탭** — `nav-tab -> nav-sub` 두 단계 위에 **세 번째 단계**가 생긴다. 게다가
  정작 긴 화면은 규칙(마크업 12,637자)이지 용어집(5,397자)이 아니다. 탭을 도입한다면
  재사용 가능한 패턴으로 만들어 규칙 화면까지 함께 적용해야 한다 — 나중 과제로 남긴다.

**같은 문제를 이미 푼 화면이 있었다.** JOIN 그래프가 "자동 수집 + 수동 등록 + 확정 목록"을
한 화면에 담고 있고, 순서가 `수집 -> 후보+승인 -> 확정 목록 -> 수동 등록` 이다. 용어집도
같은 순서로 맞췄다. 처음에 어색했던 이유는 위치가 아니라 **순서**였다(수동 등록이 맨 위,
수집이 접힌 채 중간).

```
§ 업무 용어집
§ 스키마에서 용어 수집   대상 DB · 스키마 · 충돌 정책 · [후보 뽑기] · [고른 항목 등록] · 후보 표
§ 등록된 용어           필터 · 목록
§ 직접 등록             수동 폼 (맨 아래)
```

### 이름에서 `Design Lab` 을 뺐다

`Design Lab에서 용어 수집` 은 **내부 하위 시스템 이름을 사용자에게 노출**하는 것이다.
JOIN 그래프는 그렇게 하지 않는다 — `수집된 SQL 및 실행이력(pg_stat_statements)에서
추출한` 처럼 **출처**를 말한다. 그래서 `스키마에서 용어 수집` 으로 바꾸고, 설명문에서
"같은 분석의 전체 결과는 Design Lab 화면에서 볼 수 있습니다"로 한 번만 가리킨다.

```
대상 DB · 스키마 · 이미 있는 컬럼은(건너뛴다/덮어쓴다) · [후보 뽑기] · [고른 항목 등록]
후보 표: 체크박스 · 용어 · 컬럼 · 정의(+근거) · 기존 여부
```

**기존 항목이 있는 후보는 체크를 꺼서 내보낸다.** `for_table()` 이 컬럼 중복을 막지
않으므로 모르고 등록하면 같은 컬럼에 정의가 둘 실린다(실측: 손수 15건과 자동 20건이
9건 겹쳤다). 기본 정책도 `skip` 이다.

실측(BIRD/california_schools): 후보 19건 중 14건이 이미 등록된 것으로 정확히 표시됐고,
새 5건만 체크된 상태로 나왔다. 등록 후 아래 목록이 자동 갱신된다.

### UI 편집에서 두 번 데인 것 (같은 원인)

문자열 슬라이스로 HTML을 고칠 때 **슬라이스 시작점이 태그 문자(`<`)라 앞의 들여쓰기가
빠진다.** 치환 문자열에 들여쓰기를 넣어 두면 여는 태그만 매칭에 실패하고 닫는 태그는
성공해 **마크업이 깨진 채 남는다**(`<details>` 가 열린 채, `</div>` 가 하나 더).

`node --check` 는 이걸 못 잡는다 — JS 문법만 본다. 잡은 방법:

```
본문에서 <script> 를 걷어내고 태그 여닫이 수를 센다
정리 전 백업과 비교해 "원래부터인지 내가 만든 것인지" 가른다   <- p 태그는 원래부터 -1 이었다
```

**앞으로 UI를 고치면 ① 태그 균형을 백업과 대조하고 ② 실제 데이터로 렌더해 본다.**
렌더 확인은 `tools/ui_render_check.js`.

### UI는 한 파일이라 편집 중간 상태가 그대로 서비스된다

`pgxnl/api/static/index.html` 한 장이 전체 UI다. 편집 스크립트가 **여는 태그 치환에
실패하고 닫는 태그만 성공**하면 깨진 마크업이 그대로 디스크에 남고, `FileResponse` 가
매 요청 그 파일을 읽으므로 **그 순간 열려 있던 탭이 깨진 DOM을 받는다.** 새로고침
전까지 그대로다 — 2026-09-14에 "너비 조절 후 포인터와 메뉴가 어긋난다"로 나타났고
탭을 새로 여니 해결됐다.

막는 장치 셋:

```
main.py         index 응답에 Cache-Control: no-cache, must-revalidate
                (ETag 는 이미 있다. 낡은 판이 재검증 없이 쓰이는 것만 막는다)
편집 후 검사     <script> 를 걷어낸 본문에서 태그 여닫이 수를 세고 **정리 전 백업과 대조**
                — 절대값이 아니라 차이를 봐야 한다(p 태그는 원래부터 -1 이었다)
tools/ui_render_check.js   실제 API 응답으로 렌더 함수를 돌려 본다
```

`node --check` 는 이 부류를 못 잡는다 — JS 문법만 보고, 정의가 통째로 지워져도
참조만 있으면 통과한다(`AG_KIND_LABEL` 이 그렇게 사라졌다).

## UI 토큰 도입 (2026-09-14)

`:root` 에 눈금을 정의하고 흩어진 값을 흡수했다.

```css
--ctl-h:36px;                    /* 버튼·입력칸 공통 높이 */
--fs-xs:11px  --fs-sm:12px  --fs-md:13px  --fs-lg:14px  --fs-xl:15px
--sp-1:4px  --sp-2:8px  --sp-3:12px  --sp-4:14px  --sp-5:20px  --sp-6:28px
```

**글꼴 — 13가지 -> 5토큰 + 단일 용도 4개.** 반픽셀 값(10.5·11.5·12.5·14.5px)을 가장
가까운 단계로 흡수하고 110곳을 토큰으로 바꿨다. 남은 고정값은 단일 용도 제목뿐이다
(login h1 22 · logo 19 · section-title 17 · nav-tab 16).

**여백 — 토큰만 정의하고 희귀값 12곳만 흡수.** 전수 217회 중 57%가 4배수를 벗어나는데,
**전부 스냅하지 않았다** — `14px`(32회)·`10px`(21회)·`6px`(23회)이 이미 리듬을 이루고
있어 강제로 맞추면 화면 전체가 밀린다. 1~3회짜리 예외값만 흡수했다
(1->2, 3->4, 5->4, 13->12, 21->20). 남은 3회 이하 값은 전부 4의 배수다.

`--sp-4:14px` 가 4배수가 아닌 것은 의도다. 이상적인 격자보다 **실제로 쓰이는 리듬**을
토큰으로 만드는 편이 지켜진다 — 격자를 강요하면 아무도 안 쓰고 인라인으로 돌아간다.

### 절 구분 (2026-09-14)

패널 안의 절들이 `margin-top:20px` 만으로 떨어져 있어 어디서 끊기는지 안 보였다
(JOIN 그래프: `JOIN 그래프` / `대기 중인 후보` / `승인된 JOIN`).

```css
.section-title{font-size:17px;font-weight:700;margin-bottom:14px;}          /* 화면 이름 */
.sub-panel > .section-title:not(:first-child){                              /* 절 구분 */
  font-size:var(--fs-xl);margin-top:28px;padding-top:18px;
  border-top:1px solid var(--border);}
```

마크업은 건드리지 않고 `:not(:first-child)` 로 잡았다. 인라인 `margin-top` 13곳이
이 규칙으로 대체돼 걷어냈다(인라인 152곳 -> 139곳).

**첫 제목이 화면 이름이 아닌 패널이 넷 있었다** — 규칙이 `:first-child` 를 화면 이름으로
가정하므로 어긋나면 구분선이 엉뚱한 데 생긴다.

```
analyze-main   (제목 없음)              -> 질문 분석
targets        대상 DB 등록             -> 대상 DB        (등록은 카드 제목으로 이미 있음)
cache          DB 스키마 캐시 (…)        -> 캐시 + 기존 제목을 절로
settings       등록된 모델              -> 모델 설정 + 기존 제목을 절로
```

이제 16개 패널의 첫 제목이 전부 사이드바 메뉴 이름과 맞는다.

### 2026-09-14 · 분석 화면 카드 처리 + 메뉴명 Query

```css
.card.controls{display:flex;flex-direction:column;gap:8px;}
.card.controls > *{margin-top:0;margin-bottom:0;}
```

### 2026-09-14 · 수집된 SQL -> 자연어 질문 -> 시맨틱 캐시 등록

pgxllm 에 있던 기능(`/api/pgstat/{alias}/query/describe` + `.../save-cache`)을
pgxnl 로 옮겼다. `SQL 수집` 화면의 「SQL 재수행」 카드 안에 「자연어 질문」 절로 붙였다.

```
POST /api/admin/targets/{name}/statements/describe   {sql, params}            -> {question}
POST /api/admin/targets/{name}/statements/cache      {question, sql, params,  -> {stored, sql,
                                                      schema_name}                row_count, answer}
```

#### 캐시에 들어가는 것은 수집된 SQL 그 자체다

"질문으로 파이프라인을 한 번 돌려서 답변까지 만든다"도 후보였지만 접었다 — 그러면
캐시에 들어가는 SQL이 **LLM이 새로 만든 SQL**이 되어 이 기능의 목적이 사라진다.
운영에서 실제로 도는 SQL을 심으려는 것인데 바꿔치기하는 셈이다.

넣기 전에 두 가지를 한다.

1. **Canonicalization** — `SemanticCache.store()` 의 요구다. 안 거치면 캐시 히트 때
   나가는 SQL과 미스 때 만들어지는 SQL의 모양이 달라진다.
2. **실제 실행** — 지금 스키마에서 도는지 확인한다. 수집 시점과 달라졌으면 여기서
   걸리고 캐시에 넣지 않는다.

#### `answer` 는 캐시 히트 때 쓰이지 않는다 (조사 결과)

`orchestrator.py` [10] 주석: "ReAct 루프의 finalize() 답변은 실제 실행 결과를 보지
못한 채 작성된 텍스트다 — **캐시 히트 여부와 무관하게 항상 방금 실행한 rows를 근거로
답변을 새로 요약한다**." `cached.answer` 는 `sql_steps` 가 빈 경우에만 쓰인다.

그래도 채워 넣는다 — 컬럼이 NOT NULL 이고, 관리 화면에서 사람이 이 항목이 무엇인지
알아볼 수 있어야 한다. 실행 결과를 `_summarize()` 로 요약해 넣는다.

#### 검증 계층은 여기서 돌지 않는다

관리자 전용 경로이고(기존 `statements/run` 과 같다), 실제 사용자 경로의 검증은
**캐시 히트 시점에** 다시 돈다(`analyze()` 의 [9] 는 캐시 히트 여부와 무관하게 항상
수행). 그래서 여기에 넣는 것만으로 권한·PII 경계가 뚫리지 않는다.

#### 중복 방지 — `SemanticCache.exists()` 를 새로 뒀다

`pgxnl_cache` 에 `(target_db, schema_name, question)` 유니크 제약이 **없다.** 같은
질문을 두 번 넣으면 행이 둘 생기고 `_bump_hit_count` 의 UPDATE 가 둘을 함께 올린다.
실제로 기존 데이터에 이미 중복이 있다(id 1897/1899 가 같은 질문). 넣기 전에
`exists()` 로 막는다.

#### 새 LLM 단계 `describe_sql`

`STAGES` 에 추가했다(설정 화면은 STAGES 를 그대로 렌더하므로 마이그레이션 불필요).
`summarize` 를 재사용하지 않은 이유는 성격이 다르기 때문이다 — 이쪽은 SQL 을 읽고
질문을 쓴다. 호출에 **30초 자체 상한**을 걸었다(사고 켜진 모델은 이 정도 작업에도
수십 초를 쓴다).

#### 실측

```
describe   1.4s,  "가장 많이 대여된 상위 10개의 영화 제목과 각각의 대여 횟수는 무엇인가요?"
cache      stored=true, row_count=10
중복       stored=false, "같은 질문이 이미 캐시에 있습니다"
깨진 SQL   400, "SQL 실행 실패 — 캐시에 넣지 않았습니다: relation ... does not exist"
```

#### 한계 — 지금 설정에서는 거의 같은 문장만 걸린다

`PGXNL_CACHE_EMBEDDING_ENABLED=false` 라 조회는 `pg_trgm` 어휘 유사도 0.85 만
쓴다. 같은 뜻의 다른 문장은 안 걸린다 — 위 질문을 "가장 많이 대여된 영화 10개와 대여
횟수는?" 으로 바꾸면 유사도가 **0.500** 으로 기준에 한참 못 미친다. 의역까지 잡으려면
임베딩 경로(threshold 0.90)를 켜야 한다. 이 기능의 값어치는 그 설정에 달려 있다.

검증: 460 테스트 통과, 태그 균형 0, JS 문법 OK, 엔드포인트 실호출 확인.

#### 임베딩 캐시 조회를 켜 보고 되돌렸다 (실측)

`PGXNL_CACHE_EMBEDDING_ENABLED=true` 로 바꾸고 재기동해 실제로 쟀다. 결론은 **켜면 안
된다**. 되돌렸다.

먼저 알아둘 것: 조회 SQL 에 `AND embedding IS NOT NULL` 이 있다
(`semantic.py:79`). 임베딩을 끈 채로 저장된 기존 행은 임베딩 경로에서 **영영 안
걸린다.** 켜 봐야 그 뒤에 넣은 것만 혜택을 본다.

저장된 질문 하나에 13개 문장을 재봤다(granite-embedding-278m, 768차원).

```
■ 같은 뜻 (걸려야 함)            ■ 다른 뜻 (걸리면 안 됨)
  0.976 영화 10개와 대여 횟수는?    0.932 대여된 영화 카테고리 10개는?
  0.908 제일 많이 빌려간 영화 10편   0.923 가장 적게 대여된 영화 10개
  0.897 대여가 제일 많은 top 10    0.879 대여 매출이 가장 높은 영화 10개
  0.889 대여 횟수 기준 상위 10개    0.875 재고가 가장 많은 영화 10개
  0.879 영화별 대여 건수 많은 순     0.849 가장 많이 출연한 배우 10명
  0.831 인기 영화 10편의 대여 건수   0.802 영화 10개의 제목과 대여 요금
                                 0.776 가장 많이 대여한 고객 10명

같은 뜻 최저 0.831   다른 뜻 최고 0.932   ->  0.101 겹친다
```

**두 분포가 겹친다.** 모든 의역을 잡는 임계값은 반드시 오답도 잡는다. 지금 기준값
0.90 에서 실제로 벌어지는 일은:

```
얻는 것   0.976, 0.908   의역 2건이 히트
잃는 것   0.932, 0.923   엉뚱한 질문 2건이 히트 -> 틀린 SQL 이 조용히 나간다
```

특히 **"가장 적게 대여된" 이 "가장 많이 대여된" 에 0.923** 이다. 임베딩이 방향을
담지 못한다. 최다 대여 SQL 이 최소 대여 질문에 나가고, 결과가 그럴듯해서 아무도
모른다 — `ex_can_pass_by_coincidence` 와 같은 종류의 실패다.

안전한 임계값은 0.932 위, 즉 **0.94** 정도다. 그러면 0.976 하나만 얻는다 — trgm 이
놓치는 것(0.500)을 하나 건지는 값어치는 있지만, 여유가 0.008 뿐이라 문장을 더 재면
바로 뒤집힌다. 켜지 않기로 했다.

**단서**: 표본이 저장 질문 1개 × 문장 13개다. 그리고 임베딩 모델이 278M 짜리
다국어 모델이라 한국어 분해능이 여기까지일 수 있다. 더 큰 모델로 바꾸면 분포가
갈릴 가능성은 있다 — 바꾸게 되면 이 측정을 다시 하면 된다.

**그래서 지금 이 기능의 사정권은 "거의 같은 문장"이다.** 같은 질문이 반복되는
운영 환경(대시보드·정기 조회)에서는 값어치가 있고, 사람이 매번 다르게 묻는
환경에서는 거의 안 걸린다.

### 2026-09-14 · 유사 쿼리 탐색 (승인된 사용례)

pgxllm 의 Query 수집 의도 — "이 DB 를 실제로 어떻게 쓰고 있는지 실 데이터에서 찾아
사용자에게 보여준다" — 를 pgxnl 로 옮겼다. **캐시와 다른 물건이다.**

```
pgxnl_cache              질문 -> SQL   파이프라인이 읽음   TTL 있음   자동 축적   임계값 있음
pgxnl_verified_queries   질문 -> SQL   사람이 읽음        TTL 없음   승인 필요   임계값 없음
```

#### 임계값을 두지 않는 것이 핵심이다

캐시에서 임베딩을 못 쓴다고 결론 낸 측정(같은 뜻 0.83~0.98 / 다른 뜻 최고 0.93,
"가장 적게"가 "가장 많이"에 0.923)이 **여기서는 쓸 근거가 된다.**

```
캐시   자동으로 하나 선택  ->  빗나가면 조용한 오답   ->  임계값이 생명
탐색   사람이 목록에서 고름 ->  빗나가도 눈으로 거름   ->  순위만 맞으면 됨
```

실측이 그대로 보여줬다. "대여가 많은 영화 알려줘" 검색에서 1등이 `배우별 출연
수`(0.783), 2등이 정답인 `가장 많이 대여된 영화`(0.780) — 0.003 차이로 뒤집혔다.
캐시였다면 틀린 SQL 이 조용히 나갔을 상황이고, 탐색이라 정답이 바로 아래 보인다.

임베딩이 없거나 실패하면 `pg_trgm` 어휘 유사도로 내려앉는다. 참고용 화면이 임베딩
서버에 묶이면 안 된다.

#### 별도 테이블인 이유

수명이 다르다. `수집 초기화`가 대상의 수집 SQL 을 통째로 지우므로
(`SqlStatementStore.delete_target`), 승인해서 설명까지 다듬은 지식이
`pgxnl_sql_statements` 에 얹혀 있으면 재수집마다 날아간다.

#### 승인이 거르는 것

수집 원본은 40% 가 잡음이다(실측: dvdrental 20건 중 8건이 `pg_advisory_unlock_all`,
`set_config`, `version()` 류). 그건 기계가 거른다. **기계가 못 거르는 건 설명이
맞느냐**다 — 틀린 설명이 붙은 예제는 없느니만 못하다. 승인 절차의 본체가 거기다.

#### 배치

`Query` 화면의 `쿼리 방식` 세 번째 모드로 넣었다(`자연어 질문` / `SQL 직접 입력` /
`유사 쿼리 탐색`). 새 메뉴가 안 늘고, **탐색 -> `SQL로 가져오기` -> SQL 모드에서
고쳐 쓰기**가 한 화면에서 이어진다. 등록·승인은 `SQL 수집` 화면(수집 -> 설명 ->
승인이 한 흐름).

```
POST   /api/admin/targets/{name}/verified-queries          등록 (approved=false)
GET    /api/admin/targets/{name}/verified-queries          q=유사순위 · table=필터
PATCH  /api/admin/verified-queries/{id}                    설명·SQL 수정
POST   /api/admin/verified-queries/{id}/approve            승인/해제
DELETE /api/admin/verified-queries/{id}
```

#### 권한은 미뤘다

지금은 admin 전용이다. 일반 사용자에게 여는 건 기능이 완성된 뒤에 정한다 — 여는 건
라우터 한 줄이지만 열어놓고 좁히는 건 이미 본 사람이 생긴 뒤라 되돌릴 수 없다.
`has_pii`(용어집 PII 플래그로 판정)는 계산해 저장하고 화면에 표시만 한다. 차단에는
쓰지 않는다.

#### $N 은 그대로 둔다

`pg_stat_statements` 가 값을 지운 자리표시자를 대표값으로 채우지 않는다. 원문 보존이
정직하고 "여기에 값이 들어간다"가 오히려 명확하다.

#### 고친 것 둘

- `user: CurrentUser` 는 의존성이 아니다. `CurrentUser` 가 `Annotated[..., Depends]`
  별칭이 아니라 평범한 dataclass 라 FastAPI 가 **본문 파라미터로 해석**해 422 가 났다.
  `= Depends(require_admin)` 를 붙여야 한다.
- `CASE WHEN $2 THEN $3 ELSE NULL END` 는 `$3` 타입을 못 정해 text 로 추론한다
  (`DatatypeMismatchError`). `$3::integer` 로 캐스트.

검증: 460 테스트 통과, 태그 균형 0, JS 문법 OK, 등록 5건 -> 승인 5건 -> 유사 검색
3종 실호출 확인.

#### 축 B(few-shot 자동 주입)는 하지 않았다

pgxllm 은 `verified_queries` 를 프롬프트에 `### 유사 질문 예시` 로 넣는다(스키마 주석이
`few-shot source`, 화면 이름이 `FewShotPage`). pgxnl 에서 few-shot 을 앞에 두는 건
이미 음수로 측정됐다(EX 28 -> 26, `canonical_rewrite.py` 모듈 설명). 데이터가 쌓이면
나중에 재볼 수 있지만 기본으로 켜지 않는다.

#### 직접 쓴 SQL 도 등록할 수 있게 했다 (고리 닫기)

`SQL 수집` 에서만 등록되면 **손으로 쓴 쿼리는 영영 못 남긴다.** 탐색에서 가져와
고친 것도 마찬가지다. `Query` 의 `SQL 직접 입력` 모드에 등록 카드를 붙였다.

```
탐색 -> [SQL로 가져오기] -> 고치기 -> [실행] -> [설명 생성] -> [등록] -> 승인 -> 다시 탐색에
```

**실행에 성공해야 등록 카드가 열린다.** 도는지 확인되지 않은 예제는 참고가 아니라
함정이다. 수집 경로는 SQL 이 운영에서 돌던 것이라 그 보증이 이미 있었지만, 손으로
쓴 것은 여기서 만들어야 한다.

등록에 쓰는 SQL 은 `sqlInput` 이 아니라 **응답의 `j.sql`**(정규화를 거친 실행된 SQL)
이다. 입력칸을 직접 읽으면 실행 뒤 사용자가 고친 글자가 검증 없이 등록된다.

참조 테이블은 **서버가 파서로 뽑는다**. 수집 경로는 목록에 이미 들고 있지만 손으로
쓴 SQL 은 그게 없다 — 호출자에게 맡기면 그쪽만 테이블 필터가 안 먹는다. 파싱 실패는
등록을 막지 않는다(필터가 덜 듣는 것뿐이다).

실측: `customer JOIN rental` 을 `tables_used:[]` 로 보냈더니 서버가
`['public.customer', 'public.rental']` 로 채웠고, 승인 후 `table=customer` 필터와
"고객별 대여 건수" 유사 검색(0.741, 1등) 양쪽에 걸렸다.

**고친 것**: 모드 전환에서 `answerCard`/`sqlCard`/`logCard` 를 `mode!=='sql'` 로
숨기게 썼다가 되돌렸다 — 그 셋은 `자연어 질문` 모드도 함께 쓴다. 탐색 모드에서만
치우고, 등록 카드만 SQL 모드 전용이다.

### 2026-09-14 · Physical Lab

`Design Lab` 의 짝으로 물리 상태를 보는 화면을 붙였다(`분석` 탭, Design Lab 바로 아래).

```
Design Lab     논리 구조   정규형 · 같은 개념의 사본 · 혼합 그레인
Physical Lab   물리 상태   차지하는 공간 · 죽은 행 · VACUUM · 안 쓰이는 인덱스
```

같은 규칙을 따른다 — 결정론적(LLM 미사용), 읽기 전용, 요청할 때만 계산하고 캐시하지
않는다. 다만 Design Lab 과 달리 **데이터를 훑지 않는다**(카탈로그·통계 뷰만 읽는다).
그래서 큰 스키마에서도 빠르다.

```
GET /api/targets/{name}/physical-lab?schema=...
pgxnl/agent/physicallab.py   analyze_physical()
```

#### `idx_scan = 0` 은 "안 쓰이는 인덱스"가 아니다

`pg_stat_reset()` 이후의 횟수일 뿐이라, 어제 통계를 지웠으면 **모든 인덱스가 0 으로
보인다.** 그 숫자만 보고 지우면 멀쩡한 것을 지운다. 그래서 `stats_reset` 을 요약
카드 맨 위에 함께 띄우고, 아래에 "이 시점부터 센 것"이라고 적어 뒀다. 판정하지 않고
근거를 돌려주는 것은 `stats_guard` 와 같은 방침이다.

PK·unique 를 받치는 인덱스는 조회 0회여도 발견 목록에서 뺀다 — 제약이 쓰는 것이라
지울 수 있는 물건이 아니다. 화면 표에는 `PK`/`unique` 뱃지로 남겨 둔다.

#### 임계값

```
죽은 행      30% 이상 주의 / 10% 이상 검토, 단 1,000행 미만은 안 짚는다
안 쓰이는    1MB 미만 인덱스는 안 짚는다 — 지워봐야 얻는 게 없고 목록만 길어진다
인덱스
```

죽은 행 임계값을 autovacuum 기본값(scale_factor 0.2)보다 넉넉히 잡았다. 0.2 를 그대로
쓰면 정상 동작 중인 테이블까지 전부 걸린다.

#### 스키마 이름을 리터럴로 박는다

`execute_readonly` 는 파라미터를 받지 않아서 스키마를 SQL 에 직접 넣어야 한다. 박기
전에 식별자 모양(`^[A-Za-z_][A-Za-z0-9_$]*$`)인지 확인하고 아니면 400 을 돌려준다.
실측: `schema=pub'lic` -> HTTP 400.

#### 실측

```
dvdrental/public          6.7 MB · 테이블 15 · 인덱스 32 · 발견 0건
                          조회 0회 인덱스 13건(PK/unique 포함) — 크기가 다 1MB 미만이라
                          발견으로는 안 올라온다
BIRD/california_schools  11.6 MB · 테이블 3 (schools 8.1MB / frpm 3.1MB / satscores 448KB)
```

`stats_reset` 이 NULL 이면(한 번도 초기화 안 함) 화면에 "기록 없음"으로 뜬다.

### 2026-09-15 · 사용례 등록 경로를 세 곳으로 통일

사용자 지적: 등록이 `SQL 직접 입력`에만 있다 — SQL 미숙련 사용자가 실제로 쓰는
`자연어 질문`에는 없었다. `SQL 수집`에도 있어야 한다는 지적과 함께.

**돌아가는 대신 자연어 질문에 직접 붙였다.** `SQL로 우회시키는` 안도 있었지만
버렸다 — 목표 사용자(SQL 미숙련자)는 애초에 SQL 모드를 쓸 일이 없다. 대신
`analyze()`가 성공하면(sql_steps 가 있으면) 기존 `vqRegCard`(사용례 등록 카드)를
그대로 띄우고, **사용자가 실제로 타이핑한 질문(`qInput`)을 그대로 채운다** — SQL만
보고 LLM이 거꾸로 추측하는 `describe_sql` 보다 이쪽이 "진짜 실사용 질문"에 가깝다.
`설명 생성` 버튼은 그대로 남겨 재작성 옵션으로 쓸 수 있다.

```
자연어 질문 성공 -> vqRegSql = 실행된 SQL, vqRegQuestion = 사용자가 친 질문 그대로
SQL 직접 입력 성공 -> vqRegSql = 실행된 SQL, vqRegQuestion = 비움(설명 생성 필요)
```
같은 카드·같은 제출 함수(`registerQuerySql`)를 공유한다 — 모드가 다를 뿐 등록
로직은 하나다. `toggleQueryMode()`는 모드를 바꿀 때마다 등록 카드를 일단 숨긴다
(이전 모드의 결과가 새 모드로 넘어와 보이면 안 되므로).

**`SQL 수집`의 등록에는 실행 검증이 빠져 있었다 — 추가했다.** `registerVerified()`가
`stmtRunSql` 텍스트를 실행 확인 없이 그대로 보냈다. `SQL 직접 입력`이 이미 지키던
원칙("도는지 확인 안 된 SQL은 참고가 아니라 함정")이 여기만 빠져 있었던 것이라
셋을 통일했다.

```
stmtRunVerifiedSql   지금 textarea 내용과 같은 텍스트가 [실행]에 성공한 적이 있는지
                     행을 새로 열거나(openStatementRun) textarea 를 고치면(oninput)
                     null 로 돌아간다 — 실행 뒤 한 글자라도 고치면 다시 실행해야 한다
```
`$N` 은 원문 그대로 저장하기로 한 결정([[verified_queries 설계]])과 맞춰, 검증도
치환 전 원문 텍스트에 건다(치환된 실행문이 아니라).

**정리하면 이제 세 곳 다 같은 규칙이다** — 자연어 질문 / SQL 직접 입력 / SQL 수집,
전부 "실행에 성공해야 등록할 수 있다."

검증: 460 테스트 통과, 태그 균형 0, `/api/analyze` 실호출로 `sql_steps` 채워짐 확인.

### 2026-09-15 · `wrap-table` 너비 버그 — SQL 열이 재수행 버튼을 밀어냄

사용자 보고: `SQL 수집`에서 긴 SQL을 수집하면 재수행 버튼이 뭉개진다.

**원인**: `table.wrap-table{table-layout:fixed;}` 에 `width` 가 없었다.
`table-layout:fixed` 는 "너비를 안 정한 열이 남는 공간을 채운다"는 규칙인데, 그
계산의 기준이 되는 **표 전체 너비**가 없으면 제대로 안 먹힌다 — `<table>` 은
기본이 `display:table` 이라 블록 요소처럼 부모 너비를 자동으로 채우지 않는다.
결과: 너비를 안 정한 SQL 열이 내용 길이만큼 계속 넓어지면서 옆의 고정폭 열
(재수행 버튼, 70px)을 밀어냈다.

```css
table.wrap-table{table-layout:fixed;width:100%;}   /* width:100% 추가 */
```

**한 곳만 고치면 전부 고쳐진다** — 같은 패턴(고정폭 열 + 나머지를 채우는 SQL/
질문/설명 열)이 `wrap-table` 을 쓰는 모든 표에 똑같이 있었다: SQL 수집, 유사 쿼리
탐색(승인 목록), 감사 로그, BIRD 평가 상세, ERD 인덱스/컬럼 표. 전부 같은 잠재
버그를 안고 있었고 `width:100%` 하나로 다 같이 고쳐졌다.

검증: 460 테스트 통과, 태그 균형 0, 서버 응답 == 디스크.

본 앱 스크립트는 `</body>` 바로 위에서 한 번에 실행된다. 거기서 테마를
적용하면 라이트로 한 번 그려진 뒤 다크로 바뀌는 깜빡임이 생긴다. 그래서
`localStorage` 값을 읽어 `data-theme` 를 미리 세팅하는 10줄짜리 스크립트를
`<style>` 바로 뒤, `</head>` 전에 따로 뒀다 — body가 그려지기 전에 실행된다.
본 스크립트의 `initTheme()`은 이 값을 select 에 반영하고 문구를 채우는 역할만
한다(실제 반영은 이미 끝나 있음).

#### 하드코딩 색상 45곳 감사·정리

토큰 밖에서 직접 hex 를 쓴 곳이 45건 있었다 — 대부분 JS 로 그리는 뱃지/선

바로 옆 텍스트는 이미 `var(--warn)`을 쓰고 있었다 — 셋을 `--warn` 하나로
통일했다.

**SQL 튜닝의 실행 시간 히트 색은 4단계 -> 3단계로 줄였다** — 넷째 단계
(`#bc4c00`, 25~50%)만 토큰이 없는 리터럴이었고, 25% 넘으면 이미 "주의 필요"
수준이라 그 위 단계를 더 쪼갤 값어치가 크지 않다고 판단했다.

```js
if(!q && !t){

```

이제 그 호출은 안내 문구만 띄우고 조용히 끝난다 — 호출 자체를 지우지 않은
이유는 어차피 무해하고, 나중에 "최근 본 것 기억" 같은 기능이 붙을 자리로

### 2026-09-15 · Schema 탐색 — 목록 보기에도 스키마 선택 추가

사용자 지적: 목록 보기엔 스키마 선택이 없다, ERD처럼 반영하는 게 낫겠다.

확인해보니 `/browse` 는 대상의 **모든 스키마**를 순회해 한 번에 돌려주는데

전부 한 화면에 섞어 보여주고 있었다. **BIRD 대상은 스키마가 11개, 테이블이
75개**(california_schools 외에 card_games·financial·superhero 등 BIRD

실제로 작업하는 california_schools 만 보려 해도 좁힐 방법이 없었다.

ERD 보기는 이미 스키마 선택이 있었다(`sbErdSchema`) — 한 화면에 하나의 ERD만
그릴 수 있어서다. **그 선택을 목록·ERD 공용으로 승격했다** — 스키마 목록은
이미 받아온 데이터(`sbData`)에서 클라이언트가 뽑으므로 API 호출이 추가로
필요 없다.

```
기본값        "전체" — 지금까지의 동작(모든 스키마 통합)을 그대로 유지
좁히면         목록은 그 스키마 테이블만, ERD는 원래도 하나를 골라야 했다
```

**검색과 스키마 좁히기가 동시에 걸리면 헷갈릴 수 있다**는 지적을 받아
`전체`를 기본값으로 유지하는 것 외에 안전장치를 하나 더 넣었다 — 스키마를
좁힌 채 검색했는데 그 스키마엔 없고 **다른 스키마엔 있으면**, 빈 결과 대신
"'california_schools'에는 없습니다 — 다른 스키마에 있을 수 있습니다. 전체로
바꿔서 다시 찾아보세요"라고 알려준다(`sbEmptyHint()`). 검색어를 전체 데이터에
대해 한 번 더 돌려 판단한다 — 클라이언트에 이미 다 있는 데이터라 비용이
없다.

**곁들여 고친 것**: 테이블명 폰트가 명시적 크기 없이 브라우저 기본값
(체감상 16px bold)을 쓰고 있어 주변 UI 텍스트(13px 대)보다 확 커 보였다 —
`var(--fs-lg)`(14px)로 명시했다.

검증: 460 테스트 통과, 태그 균형 0, 중복 id 없음, `/browse` 실호출로 BIRD가

### 2026-09-15 · `SQL 수집` 대상 DB 변경 시 목록이 안 바뀌던 버그

사용자 지적: 대상 DB를 바꿔도 등록된 사용례가 그대로다 — 버그 아닌가?

맞았다. `stmtTarget`(대상 DB 선택)에 **`onchange` 자체가 없었다.** 같은
화면의 다른 선택창들(`Schema 탐색`의 `sbTarget`, `실행계획`의 `planTarget`
등)은 전부 대상을 바꾸면 목록을 새로 불러오는데, 이 화면만 빠져 있었다 —
처음 만들 때부터 있던 결함으로 보인다(이번에 처음 발견됨).

```html
<select id="stmtTarget" onchange="loadStatements();loadVerified();"></select>
```

수집 목록(`stmtBody`)과 승인 목록(`vqBody`) 둘 다 걸었다 — `loadStatements()`
자체는 승인 목록을 부르지 않아서 따로 추가해야 했다.

검증: 460 테스트 통과, 태그 균형 0, 서버 응답에서 `onchange` 반영 확인.

### 2026-09-15 · `SQL 수집` 두 목록에 페이징 추가

사용자 질문: 수집/승인 목록에 페이징이 필요하지 않을까?

확인해보니 **더 심각한 잠재 버그**가 있었다. `수집 목록`은 서버가 돌려주는
`total`을 아예 안 받아왔다(`const {items}=await r.json()`) — 100건 넘게
수집되면 몇 건이 잘렸는지 알 방법이 없이 조용히 잘렸다. 수집 자체는 한 번에
최대 1000건까지 받는데(`최대 수집 수` 기본값) 목록은 서버 기본값 100건까지만
보여주고 있어서, 운영 DB에서 수집하면 바로 부딪힐 문제였다.

**"더 보기" 방식으로 두 목록에 페이징을 붙였다** — 백엔드는 이미 `limit`/
`offset`을 받고 있어서(2026-09-14 유사쿼리 탐색 설계 때부터) 프론트만
붙이면 됐다.

```
수집 목록(stmtBody)     100건씩, 배열 인덱스로 재수행 버튼을 걸어서
                       "더 보기"때 배열에 concat 후 전체를 다시 그린다
승인 목록(vqBody)       50건씩, 버튼이 행의 실제 id를 쓰므로 배열을 안 쌓고
                       받아온 HTML을 그냥 뒤에 append 한다(insertAdjacentHTML)
```

**곁들여 고친 버그**: 승인 목록 요약(`"승인 8건 · 대기 0건"`)이 **현재
페이지에 보이는 것만 세고 있었다** — `items.filter(e=>e.approved).length`.
전체 129건 중 50건만 받아온 상태에서 승인/대기를 세면 진짜 값과 어긋난다.
`approved_only=true&limit=1` 로 가벼운 카운트 전용 호출을 별도로 보내 진짜
전체 승인 건수를 받아오게 고쳤다(서버의 `total`은 limit과 무관하게 정확한
COUNT다).

#### 검증 — 실제로 120건씩 두 테이블에 채워 넣고 헤드리스 브라우저로 확인

검증: 460 테스트 통과, 태그 균형 0, 헤드리스 브라우저 실측(puppeteer-core,

### 2026-09-15 · JOIN 그래프 개선 — 근거 SQL 표시 + 오염 데이터 정리

#### ① "어느 SQL에서 나온 관계인가"를 볼 수 있게

사용자 지적: JOIN 그래프의 후보·승인 목록이 (테이블A, 컬럼A, 테이블B, 컬럼B,
출처, 신뢰도, 호출수)만 있고 **어느 SQL에서 나온 관계인지가 끊겨 있다.**

`pgxnl_join_candidates`는 집계값만 갖고 있고 원본 SQL을 남기지 않는다
(persist_candidates 가 UPSERT 로 confidence/calls 만 갱신). 그래서 저장하는
대신 **조회 시점에 다시 확인**한다 — `pgxnl_sql_statements`/`pgxnl_verified_queries`
를 훑어 이 엣지를 실제로 쓰는지 파서로 검증한다(`graph.py:find_statements_for_edge`).
기존 데이터에도 코드 변경 없이 바로 적용되는 이유다.

```
① 가벼운 선별   tables_used 에 두 테이블이 같이 있는지 (대부분을 걸러냄)
② 정확한 확인   실제로 파싱해 parsed.joins 가 이 (테이블,컬럼) 쌍과 일치하는지
```

①만 통과하고 ②를 통과 못하면 "참고 — 두 테이블만 같이 나옴"으로 구분해 보여준다
(판정 근거를 감추지 않는다는 방침, `stats_guard`와 같은 결). 스키마 한정
여부는 무시하고 맨 이름으로 비교한다 — `pgxnl_sql_statements`에 `public.actor`와

### 2026-09-15 · SQL 튜닝에도 $N 값 대입 추가

`SQL 수집`의 재수행에 이미 있던 패턴(`$1,$2...` 자리표시자 -> 값 입력칸 ->
치환)을 `SQL 튜닝`에도 그대로 붙였다. 전엔 pg_stat_statements에서 수집한
SQL을 튜닝 화면에 붙여넣으면 `$1` 이 리터럴로 남아 그대로 실행에 넘어갔다.

```
tuneSql 입력 중  -> renderTuneParams() 가 $N 개수만큼 입력칸을 만든다
튜닝 분석 클릭   -> substituteQueryParams() 로 치환한 뒤에만 서버로 보낸다
```

`SQL 수집`은 서버(`_substitute_params`)가 치환하지만, `SQL 튜닝`은 SSE로
바로 스트리밍하는 구조라 **클라이언트에서 치환**한다 — 같은 정규식 로직
(`$(\d+)` 전부 치환, 값 없으면 그대로 둠)을 재사용했다.

같은 번호가 여러 번 나와도(`ROUND(...,$1)`과 `LIMIT $1`처럼) 입력칸은
번호당 하나만 생기고 전부 같은 값으로 치환된다 — `Set` 으로 번호를 모아서
개수를 센다(기존 패턴 그대로).

검증: 460 테스트 통과, 태그 균형 0, 헤드리스 브라우저로 사용자가 준 정확한
SQL을 입력해 `$1` 입력칸이 정확히 1개 생기고(2가 아님) 치환도 두 자리 모두
정확함을 확인.

### 2026-09-15 · Design Lab — 3NF 스키마 제안 (신규 기능)

사용자 질문: Design Lab이 정규형 위반만 보여주는데, 3NF로 만들면 어떻게 되는지
schema 제안도 가능한지?

**가능했다.** `Finding.action`은 원래 "지금 당장 할 수 있는 NL2SQL 대응"(용어집
등록 등)으로 일부러 좁혀 뒀던 것이라(analyzer.py 주석), 스키마 마이그레이션
DDL은 범위 밖이었다 — 이번이 그 범위를 넘어서는 새 기능이다.

**4종 findings 중 2종만 기계적으로 DDL화된다:**

```
transitive_dependency (코드->이름)   깨끗하게 됨 — 룩업 테이블 CREATE
duplicate_concept (사본)            깨끗하게 됨 — 정본(canonical)과 FK 조인 경로를
                                    이미 알고 있다
repeating_group (반복 컬럼)          제안 안 함 — 몇 번째까지 의미있는 데이터인지
                                    사람 판단 필요
mixed_grain (혼합 단위)              제안 안 함 — 3NF가 아니라 슈퍼타입/서브타입
                                    설계 문제라 기계적으로 못 가른다
```

**보기 전용이다 — 자동 실행하지 않는다**(사용자 결정). 검증 계층이 SELECT만
통과시키게 만들어져 있는데 그 경계를 허물지 않는다.

```
pgxnl/agent/designlab/propose.py         SchemaProposal 생성 로직
GET /api/targets/{name}/design-lab/proposals?schema=...   신규 엔드포인트
```

Design Lab 본체와 별도 호출이다 — 제안을 만들려면 관련 테이블을
`describe_table` 로 다시 읽어야 해서(타입·FK 확인) 비용이 더 든다. findings 를
먼저 보고 필요할 때만("3NF 제안 보기") 부른다.

#### 실측 (BIRD/california_schools, 17 findings)

```
제안 11건 생성 — transitive_dependency 6건 + duplicate_concept 5건 중 FK 확인된 것들
```

예시(실제 타입까지 맞음, `bigint`/`text` 자동 감지):
```sql
CREATE TABLE california_schools."frpm_county_code_lookup" (
  "County Code" text PRIMARY KEY,
  "County Name" text NOT NULL
);
INSERT INTO california_schools."frpm_county_code_lookup" ...
ALTER TABLE california_schools."frpm"
  ADD CONSTRAINT "fk_frpm_county_code" FOREIGN KEY ("County Code") REFERENCES ...;
```

#### 만들다 잡은 버그: 제약조건 이름에 공백

첫 생성 결과를 실제로 검토하다가 발견 — `County Code`처럼 공백 있는 컬럼명을
그대로 이어 붙여 `ADD CONSTRAINT fk_frpm_County Code`를 만들었는데, **따옴표
없는 식별자에 공백이 들어가 실행하면 문법 오류**가 난다. 새로 만드는 이름
(룩업 테이블명·제약조건명·뷰명)은 `_slug()`로 영숫자+밑줄만 남기고, 실제
컬럼·테이블 참조는 원래 이름을 그대로 따옴표로 감싸 쓰도록 나눴다 — 둘을
섞은 게 원인이었다.

#### 검증

```
① 생성된 25개 SQL 문장(11개 제안 안의 CREATE/INSERT/ALTER) 전부를 프로젝트
  자체 PostgreSQL 파서(AntlrPostgresParser)로 파싱 — 25/25 성공
② 헤드리스 브라우저로 실제 클릭까지 — 검토 완료 -> "3NF 제안 보기" 버튼 등장
  -> 클릭 -> 11개 카드 정확히 렌더링, DDL 내용 확인
```

BIRD 실DB에는 DDL을 실행하지 않았다 — 문법 검증은 파서로, 컬럼 타입은
`describe_table` 로 이미 실측했으므로 실행 검증까지는 필요 없다고 판단했다
(그리고 스키마 변경을 실제로 실행하는 건 이 기능의 범위 밖이다).

검증: 460 테스트 통과, 태그 균형 0.

### 2026-09-15 · Design Lab — "단계별 3NF 적용" 마법사

사용자 요청: 한 번에 반영하지 말고, 제안을 하나씩 적용하면서 **이유와 결과**를
보여주면 초보자에게 도움이 될 것 같다. 적용 중에 새로 생기는 관계는 JOIN
그래프에도 실제로 등록되면 좋겠다.

#### 동작

`Design Lab` -> 검토 실행 -> "단계별로 적용해보기". 제안(오늘 만든
3NF 제안, transitive_dependency + duplicate_concept)을 하나씩 보여준다 —
왜 필요한지(finding의 detail/action 재사용) + 적용 전/후 미니 ERD(그 제안이
건드리는 테이블만) + [이 제안 적용]/[건너뛰기]. 전부 메모리 안에서만
바뀐다(실제 DB에 DDL 실행 없음) — 딱 하나 예외가 있다(아래).

```
GET /api/targets/{name}/browse                     실제 컬럼 상세를 가져와 초기 상태로 삼음
GET /api/targets/{name}/design-lab/proposals        오늘 만든 제안 목록 재사용
```

#### ERD 렌더러를 순수 함수로 뽑아냈다

`Schema 탐색` 전용이던 `renderErd()`를 `buildErdFragment(tables, opts)`로
분리했다 — DOM 전역(`sbData`/`sbSchema`) 대신 매개변수로 받은 테이블 목록만
그린다. 마법사가 "이 제안을 적용하면"이라는 **가상의 테이블 목록**을 같은
함수로 그리기 위해서다 — 그리는 방식이 두 군데서 다르면 미리보기가 "진짜
ERD와 다르게 생겼다"는 불신을 만든다. `highlightTables` 옵션을 추가해 지금
단계가 건드리는 테이블을 굵게 표시하고, 새로 생기는 테이블/컬럼은 초록
톤 + ✨ 로 표시한다.

#### 만들다 잡은 버그 — 같은 코드가 여러 이름을 결정하면 룩업 테이블 이름이 겹친다

실측: `frpm.District Code`가 `District Type`과 `District Name` **둘 다**를
결정하는 별개의 findings 였는데, 둘 다 독립적으로 제안을 만들다 보니 똑같은
이름(`frpm_district_code_lookup`)의 룩업 테이블을 만들려는 DDL이 두 개
나왔다 — 순서대로 실행하면 두 번째가 "테이블이 이미 있다"로 실패한다.

**`_propose_transitive`를 (테이블, 코드 컬럼) 기준으로 묶도록 고쳤다** — 같은
코드가 결정하는 이름들을 한 룩업 테이블에 같이 담는다. 이게 원래 3NF 상
맞는 처리이기도 하다(같은 결정자를 공유하는 속성들은 같은 곳에 둔다).
`SchemaProposal.detail`도 `name_column`(단수) -> `name_columns`(배열)로
바꿨다. 이 변경으로 BIRD 제안이 11건 -> 10건으로 줄었다(둘이 하나로 합쳐짐).

```
CREATE TABLE california_schools."frpm_district_code_lookup" (
  "District Code" bigint PRIMARY KEY,
  "District Type" text NOT NULL,
  "District Name" text NOT NULL
);
```

#### 만들다 잡은 버그 2 — JOIN 그래프 등록이 존재하지 않는 테이블을 가리킬 뻔했다

이행 종속 적용 시 생기는 새 FK 관계를 JOIN 그래프에도 등록하기로 했는데,
그 관계가 가리키는 룩업 테이블은 **마법사 시뮬레이션 안에만 있고 실제
DB엔 없다.** 기존 `add_manual_edge()`가 쓰던 `source='manual'`로 그대로
넣으면, 실제 사람이 확인하고 등록한 관계와 구분이 안 돼 — **바로 그날
아침에 정리한 dvdrental 오염 데이터와 같은 종류의 문제**를 그 자리에서
다시 만들 뻔했다.

`add_manual_edge()`에 `source` 매개변수를 추가하고(기본값 `'manual'`이라
기존 관리 화면 동작은 그대로), 마법사는 `'design_proposal'`을 넘기게 했다
— JOIN 그래프의 "출처" 열에 그대로 노출되므로 한눈에 구분된다.

#### 검증

```
① DDL 22개 문장 전부 파서로 재확인 — 22/22 성공(병합 후에도 문법 유지)
② 헤드리스 브라우저로 전체 마법사 진행 — 1단계 적용(테이블 1->2, ✨뱃지 확인)
   -> 건너뛰기 -> 나머지 전부 적용 -> 완료 화면(9/10건, 최종 ERD 8개 테이블
   박스 = 원본 3 + 새 룩업 5)
③ JOIN 그래프에 실제로 등록됨을 DB에서 직접 확인 — source='design_proposal'로
   정확히 구분됨, 기존 진짜 manual 항목(1건)은 안 건드림
```

테스트로 생성된 join_candidates 행(design_proposal 5건)은 확인 후 삭제했다.

검증: 460 테스트 통과, 태그 균형 0.

### 회귀 수정 — Schema 탐색 ERD의 FK/JOIN 선이 전부 사라짐

마법사를 만들며 `renderErd()`를 `buildErdFragment()`로 뽑아내는 과정에서
`Schema 탐색` 원래 화면의 ERD가 망가졌다(사용자 리포트: "기존 schema탐색의
FK/Join Line들이 모두 없어졌네요").

**원인**: 테이블 박스의 실제 렌더 높이/위치를 재려면 `container`를 잠깐
`document.body`에 붙여야 한다(`offsetLeft/offsetTop/offsetWidth/offsetHeight`는
문서에 붙어 레이아웃이 계산된 요소에서만 유효하다). 그런데 코드 순서가:

```
1. container를 body에 붙임
2. 각 테이블 박스의 top 위치 계산+적용   (여기까지는 OK)
3. document.body.removeChild(container)  <- 여기서 이미 떼어냄
4. SVG <line> 좌표 계산 (fromEl.offsetLeft 등을 여기서 읽음)  <- 이미 늦음
```

3번이 4번보다 먼저 실행돼서, 모든 FK/JOIN 선의 좌표가 `0`으로 계산되고
있었다 — 선 자체는 그려지지만 전부 원점의 길이 0 선이라 안 보이는
것이었다. `Schema 탐색`과 마법사의 전/후 미리보기가 같은
`buildErdFragment()`를 쓰므로 둘 다 영향을 받았다.

**수정**: `document.body.removeChild(container)`를 SVG 선 계산과
`legend` 구성이 다 끝난 뒤, `wrap`을 만들기 직전으로 옮겼다(1줄 이동).

```js
// as-is: top 위치 계산 직후에 바로 떼어냄
tables.forEach((t,i)=>{ els.get(t.table).style.top=...+'px'; });
document.body.removeChild(container);
// ... 이후 SVG 선 좌표를 여기서 읽음 (이미 0)

// to-be: SVG/legend까지 다 만든 뒤에 뗌
tables.forEach((t,i)=>{ els.get(t.table).style.top=...+'px'; });
// ... SVG 선 좌표 계산 (container가 아직 문서에 붙어있어 정상 값)
// ... legend 구성
document.body.removeChild(container);
const wrap=document.createElement('div');
wrap.appendChild(container);
wrap.appendChild(legend);
return wrap;
```

검증:
```
① node --check: JS 문법 오류 없음
② 태그 균형: 열림/닫힘 태그 카운트 일치
③ pytest: 460개 전부 통과
④ 헤드리스 브라우저 — Schema 탐색(BIRD/california_schools) ERD:
   line 3개, 전부 길이>0, 실제 좌표(예: (120,129.5)->(440,129.5))로 계산됨
   (수정 전이었다면 전부 (0,0)->(0,0)이었을 것)
⑤ 헤드리스 브라우저 — Design Lab 마법사 전/후 미리보기:
   전(before) 0개 선(룩업 테이블이 아직 없으니 정상), 후(after) 1개 선
   (120,129.5)->(440,53), 길이 0인 선 없음 — 마법사 쪽도 같이 고쳐졌음을 확인
```

서버 재기동 전 `pgxnl_eval_runs`에 running/pending 0건 확인 후 재기동,
서빙 파일 md5sum이 디스크와 일치함을 확인.

### renderMarkdown — 중첩 목록·코드 인접 기울임 표시 버그 수정

사용자 리포트: "display도 문제가 엉망입니다." LLM 검토 답변을 실제로
받아보니 두 가지 진짜 버그가 확인됨(LLM 검토가 처음으로 이 정도 분량의
중첩 목록·`컬럼명*` 표기를 만들어내는 화면이라 지금까지 안 드러났던
`renderMarkdown`의 기존 결함).

**버그 1 — 목록에 들여쓰기(중첩) 개념이 전혀 없었다.** 기존 구현은
`\s*([-*]|\d+\.)\s+`로 시작하는 연속 줄을 전부 한 레벨로 평평하게
합쳤다. LLM이 흔히 쓰는 "1. **제목**\n   - 이유1\n   - 이유2" 패턴에서
제목과 하위 이유가 같은 목록의 형제 항목으로 뭉개지고, 그룹 사이 빈
줄마다 새 `<ol>`이 시작돼(브라우저가 매번 1부터 다시 번호 매김) 우선순위
목록이 "1. 최우선.. / 2. (하위설명).. / 1. 고우선.. / 1. 중우선.."처럼
번호가 계속 리셋되는 것처럼 보였다.

`parseListLines()`를 새로 만들어 들여쓰기 깊이로 재귀 중첩 처리하게
했다 — 빈 줄이 있어도 다음 줄이 같거나 더 깊은 들여쓰기의 목록 항목이면
같은 목록이 계속되는 것으로 본다("느슨한 목록"). 결과: 우선순위 4개가
하나의 `<ol>`에 담기고, 각 항목의 하위 설명은 그 안에 중첩된 `<ul>`로
들어간다.

**버그 2 — 기울임(`*...*`) 정규식이 백틱 코드 스팬을 넘어갔다.**
`` `admemail*`, `admfname*`, `admlname*` `` 처럼 컬럼명 뒤에 와일드카드
표기로 붙는 홑 `*`가 세 개 연속으로 나오면(굵게/기울임 의도가 아님),
기존 코드는 굵게/기울임을 백틱 처리보다 먼저 돌려서 첫 `*`와 다음
코드 스팬의 `*`를 짝지어 그 사이 전체(백틱·코드 내용째)를 기울임으로
감싸버렸다 — `<code>admemail<em></code><em>, <code>admfname</em></code>`처럼
태그가 깨져서 나왔다.

`inlineMd()`에서 백틱 코드 스팬을 굵게/기울임보다 먼저 처리하도록
순서를 바꾸고, 기울임 정규식의 내부 허용 문자에서 `<`를 제외해
(`[^*<\s][^*<]*?`) 태그 경계를 넘어 짝짓는 것 자체를 막았다.

검증: 실제 LLM 검토 응답(6,221자, 배경으로 재실행해 원문 확보)을
고친 `renderMarkdown`에 직접 통과시켜 확인 — `<ol>` 2개(전체가 아니라
의미 단위별로 정확히 분리됨), 중첩 목록 26개, 깨진 `<em>`(코드 태그를
관통하는) 0개. 헤드리스 브라우저로 그 HTML을 실제 렌더링한 스크린샷도
확인 — "종합 의견 및 우선순위"가 1./2./3. 하나의 목록으로, 각 항목 밑에
글머리 기호 하위 목록이 제대로 중첩됨. node --check, 태그 균형, pytest
460개 통과. 이 렌더러는 SQL 튜닝 답변에도 같이 쓰이므로 그 화면도 같이
좋아진다.

(BIRD, dvdrental)를 전부 LLM 서빙 서버(<LLM 서빙 서버>, RHEL 9.8)로
옮겼다.

**설치**: RHEL entitlement가 있어 podman 대신 `dnf module enable
postgresql:16` + `dnf install postgresql-server postgresql-contrib
pgvector`로 네이티브 설치(로컬 16.15와 버전 맞춤). `postgresql-setup
--initdb` → `systemctl enable --now postgresql`.

**원격 접속 허용**: `listen_addresses='*'`(재시작 필요, reload로는
안 먹음), `pg_hba.conf`에 `host all all 0.0.0.0/0 scram-sha-256` +
`::/0` 추가, `firewall-cmd --add-port=5432/tcp`(포트만 열고 IP는 안
막음 — 데모 중 노트북이 어느 네트워크에서 붙을지 몰라서 비밀번호로만
막기로 함, 사용자 확정). superuser 비밀번호를 `1dlsvmfk12#$`로 강화.

**이전**: `pg_dump -Fc`로 3개(pgxnl 23MB, BIRD 1GB, dvdrental 15MB) →
scp → 서버에서 `pg_restore --no-owner --no-privileges`. 첫 시도는
pgvector 미설치 상태로 restore해서 `pgxnl_schema_vectors` 관련
CREATE TABLE이 통째로 실패 → 34건 오류, 부분 복원됨. DB를 DROP하고
pgvector 설치 후 재시도하니 **오류 0건**으로 깨끗하게 복원됨. 복원 후
모든 테이블 소유자가 `postgres`로 남아 있어서(--no-owner) 앱이 시작 시
돌리는 스키마 자동 마이그레이션이 "must be owner of table
pgxnl_schema_cache"로 실패 — `public` 스키마의 테이블/시퀀스 전체를
`ALTER ... OWNER TO pgxnl`로 재소유해서 해결.

**검증**: pgxnl_users/targets/glossary/join_candidates/verified_queries/
llm_profiles row count 로컬=서버 전부 일치. BIRD california_schools
66개 테이블 전부 row count 일치(9,986건짜리 frpm부터 1,056,320건짜리
trans까지). dvdrental film/customer/rental count 일치.

**설정 전환**: `.env`의 `PGXNL_SYSTEM_PG_DSN` 호스트를 `<LLM 서빙 서버>`으로,
`pgxnl_targets`(서버 DB 안의 것 — 이제 앱이 보는 건 이거다) 의
BIRD/dvdrental DSN도 호스트+비밀번호를 갱신(같은 Fernet 키로 재암호화).

**막다 잡은 버그**: 전환 후 `dvdrental`만 계속 "password authentication
failed" — `BIRD`는 됐는데 `dvdrental`만 실패해서 DSN 자체 문제가
아니라고 판단, 조사해보니 `pgxnl_user_credentials`에 admin
사용자(`user_id=1`)가 `dvdrental`용으로 등록해 둔 **개인별 DB
자격증명**(예전 로컬 비밀번호 `1dlsvmfk` 그대로) 행이 있어서
`substitute_dsn_credentials()`가 이걸로 덮어쓰고 있었다 — `BIRD`엔 이
개인 자격증명이 없어서 공유 DSN을 그대로 써서 멀쩡했던 것. 그 행의
비밀번호도 새 값으로 갱신하고 앱을 재기동해 해결(캐시된 오케스트레이터가
재기동 전엔 갱신을 안 반영했다).

**보안 참고**: `postgres` 비밀번호(1dlsvmfk12#$)와 `pgxnl` 비밀번호를
서버에 등록해 뒀다 — 5432 포트가 인터넷에 열려 있고 IP 제한이 없으므로,
데모가 끝나면 방화벽으로 좁히거나 포트를 닫는 것을 권장.

서버 재기동 전 eval run 0건 확인, pytest 460개 통과, 마이그레이션에

## 보류: 1:N 조인 개수 가드 (2026-10-12)
367(qid 408)이 rulings 조인 뒤 COUNT(*)로 판정 행(2,059)을 셈(정답 COUNT(DISTINCT id) 1,382). 모델은 COUNT+JOIN 51종 중 DISTINCT 0건.
설계: COUNT(*)/COUNT(T1.x) + JOIN, 조인 상대 키가 PK/UNIQUE 아니고 FK 자식이거나 n_distinct 중복이면 한 번 조언.
보류 사유(사용자): 효과 대비 작업이 큼 — 확실한 이득 1문항, BIRD 정답 COUNT+JOIN 144개 중 121개가 DISTINCT 없이 정답이라 오탐 위험.
다른 스키마로 측정을 넓혀 같은 실수가 여러 문항에서 반복되면 재검토.
