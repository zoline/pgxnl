2026-09-02 작성. `docs/pgxnl_antlr_pipeline_design.md`의 §7 구현 순서를 **실측 결과에
맞춰 갱신**한 문서다. 설계 문서가 세운 가설 중 상당수가 측정으로 기각되었으므로, 그
근거와 함께 남은 작업을 우선순위로 정리한다.

측정 도구: `python -m pgxnl.agent.evaluation.diagnose <run_id>`

## 2. 측정으로 확정된 사실

### 2.1 `SYNTAX` 오류는 0건이다

run 88·94·100 모두 파싱 실패 0건. 설계 문서 §2.3이 *"이 비율이 높다면 few-shot 문법
예시 보강이 우선순위"* 라고 했는데 **0%이므로 그 경로는 닫혔다.**

### 2.2 컬럼 개수로 인한 "가짜 오답"은 3.3%뿐이다

`PROJECTION_MISMATCH` 1건. 설계 문서 이슈 5의 비중이 예상보다 훨씬 작다.
→ §3.3의 `execute_normalized` projection 정규화는 **도입하지 않는다.**
strict EX가 리더보드와 비교 가능한 유일한 수치인데, 그걸 오염시키면서 얻는 게 1문항뿐이다.
"가짜 오답" 진단이 필요하면 strict EX는 그대로 두고 lenient EX를 **별도 보조 지표**로
병기할 것.

### 2.3 NULL 정렬 규칙은 완벽히 작동한다 — 그러나 EX는 오르지 않았다

PostgreSQL은 `ASC→NULLS LAST` / `DESC→NULLS FIRST`인데 SQLite는 정반대다. BIRD gold는
SQLite 원본을 PG로 옮기며 명시적 NULLS 절로 이를 보존했고, 모델은 그냥 `DESC`만 써서
NULL 행이 1위로 올라와 top-N 질의가 통째로 틀렸다.

| | run 94 (규칙 없음) | run 100 (규칙 ON) |
|---|---|---|
| pred에 NULLS 포함 | 3/30 | 11/30 |
| **오답 중 NULLS 누락** | **8/17** | **0/19** |
| EX | 13/30 | 11/30 |

`OrderByNullsRule`(`agent/canonicalize.py`, 규칙 id=23)이 **NULLS 누락을 100% 제거**했다.
그럼에도 EX가 떨어진 것은 같은 구간에 thinking을 함께 켰기 때문으로 보인다(§2.4).

**중요**: 이 규칙이 프롬프트에는 이미 있었다(`pgxnl_rules` id=1, enabled). 있는데도
오답의 47%가 그 규칙 위반이었다 — 설계 문서 이슈 3 / §4(프롬프트 텍스트 → IR 코드 검증)의
실측 증거다. 같은 현상이 id 9·12·22(불필요 컬럼/별칭/컬럼 순서)에서도 관찰된다.

### 2.4 thinking이 EX를 깎고 있을 가능성 (미확정)

| 카테고리 | run 94 (thinking OFF) | run 100 (thinking ON) |
|---|---|---|
| SEMANTIC_WRONG | 9 | 13 |
| **UNCOMPARABLE** (서브쿼리·집합연산) | **1** | **5** |
| PREDICATE_MISMATCH | 3 | 0 |
| NO_SQL | 1 | 0 |

thinking을 켜니 모델이 서브쿼리·윈도우 함수를 동원한 더 정교한 SQL을 쓰는데, gold는
단순한 형태라 결과가 어긋난다. 다만 run 94→100 사이에 **세 가지가 동시에 바뀌었으므로**
(thinking ON, 코드 규칙 추가, 프롬프트 규칙 id=1 삭제) 아직 확증이 아니다.

### 2.5 파이프라인이 병목이라는 증거

run 88(120B)과 run 94(활성 3B)가 **동일하게 실패한 문항이 10건**이다:
444, 445, 446, 450, 451, 454, 456, 459, 465, 467.
유효 연산량이 40배 차이나는데도 같이 틀린다 → 설계 문서 이슈 1을 실측이 뒷받침한다.
모델을 키우거나 RL을 해도 이 10건은 안 풀린다.

### 2.6 FK는 이미 자동 파악돼 있다

```
frpm.cdscode  → schools.cdscode
satscores.cds → schools.cdscode      (이름이 달라도 FK가 관계를 선언한다)
```
DDL 캐시(`ddl:` 키)의 `foreign_keys`에 담겨 스키마 컨텍스트로 전달된다.
**인덱스 정보는 캐시에 없다** — `PgConnector`에 `pg_indexes` 조회는 있으나
(`connectors/postgresql.py`) DDL 캐시가 담지 않는다.

### 2.7 컬럼 등가 glossary가 사실상 비어 있다

glossary 13건 중 테이블 간 등가를 명시한 것은 **id=20 하나뿐**이다
(`frpm."Charter Funding Type"` ≡ `schools.fundingtype`). 나머지 12건은 값 사전
(DOC/SOC 코드값, Virtual=F/V/C/N 등)이다.

정작 가장 자주 쓰이는 세 개념에는 항목이 **하나도 없다**:

| 개념 | schools | frpm | satscores |
|---|---|---|---|
| 학교명 | `school` | `School Name` | `sname` |
| 카운티 | `county` | `County Name` | `cname` |
| 교육구 | `district` | `District Name` | `dname` |

이름이 같은 컬럼은 조인 키 `cdscode` 하나뿐이다(schools 49컬럼, frpm 29, satscores 11).

## 3. 진행 목록 (우선순위)

### ✅ 완료: thinking은 끈다 (2026-09-02)

thinking OFF가 EX 13·12, ON이 11·11이고 **소요는 5분 vs 53~57분**이다. 도움된다는 증거가
없는데 비용은 11배. `react`/`generate_sql`을 `disable_thinking=true`로 둔다.
평가가 5분이면 하루에 수십 번 실험할 수 있어 개발 주기가 근본적으로 달라진다.

### ✅ 완료: `AliasFixRule` (id=24)

잘못된 `별칭.컬럼` 참조를 그 컬럼을 실제로 가진 테이블의 별칭으로 교정한다.
`column does not exist` 에러가 **3건 → 0건**. 세 조건(현재 별칭에 그 컬럼이 없음 /
소유 테이블이 질의에 정확히 하나 / 그 테이블에 별칭 존재)을 모두 만족할 때만 고치고,
모호하면 손대지 않는다 — 잘못 고치면 에러 대신 **조용한 오답**이 되어 더 나쁘다.

**남은 한계**: 서브쿼리가 있으면 규칙 전체를 건너뛴다. `alias_to_table`이 트리 전체에서
별칭을 모아 스코프를 구분하지 못해, 서브쿼리 안의 별칭을 바깥 참조에 붙이면
`invalid reference to FROM-clause entry`가 난다(run 104 seq 447에서 실제 발생, 가드로 차단).
제대로 고치려면 **스코프별 별칭 맵**이 필요하다 — IR v2 작업.

### ★ 최우선 교훈: 모델 선택이 규칙·프롬프트를 압도한다

27B dense **65.6%** vs 35B-A3B **38.9%** (각 3회 평균, 규칙 조건 동일). 오늘 만든
canonicalization 규칙 두 개가 만든 차이는 노이즈에 묻혔는데, **모델 교체 하나가 8문항을
움직였다.** 더구나 `AliasFixRule`이 겨냥한 별칭 오류와 테이블명 오타는 27B에서 아예
발생하지 않는다 — **열등한 모델의 증상을 코드로 치료하고 있었던 셈이다.**

**따라야 할 순서**: 파이프라인을 손보기 전에 **모델 후보를 먼저 공정하게 비교**할 것.
비교는 thinking·concurrency 등 다른 변수를 고정한 채, 3회 반복 평균으로.

### ★ gold 오류가 측정의 상수 항이다

`california_schools` 30문항 중 **18건(60%)** 의 gold SQL이 Arcwise 분석에서 수정 대상으로
확인됐다(Mini-Dev 전체 평균은 16.7%). 즉 우리가 반년 가까이 써온 baseline은 **gold의 60%가
의심스러운 스키마**다. "모델 무관 실패"로 분류하고 규칙·glossary를 고민했던 문항 상당수가
실은 gold 오류였을 가능성이 크다.

대응 구조(자세한 건 `docs/eval-history.md`):
- 채점은 원본 유지(연속성), **대조군**으로 Arcwise 수정판을 둔다
- `python -m pgxnl.agent.evaluation.reference_check <run_id> <대조본>` 이 오답을
  `gold 결함 후보 / 모델 오답 / 판정 불가`로 나눠준다
- 확인된 결함은 `pgxnl_eval_gold_defects`에 등록 → 결과 화면에 ⚠ 표시 + "결함 제외 EX" 병기

**개선 작업 전에 반드시 대조 검사를 돌릴 것.** 실측상 오답 8~9건 중 모델이 실제로 틀린
것은 3~4건뿐이다. 나머지를 고치려 규칙을 만들면 gold 오류에 과적합하게 된다.

### ✅ 완료: 질문 대조 검사 3종 (2026-09-02)

프롬프트 규칙으로 지시해도 지켜지지 않는 항목을 코드로 옮긴 것들(ADR-0009).
**데이터·스키마를 조회하지 않고 질문 텍스트만 대조**하므로 비용이 0이고 데이터가 바뀌어도
낡지 않는다 — glossary에 값을 등록하는 방식은 데이터가 변하면 틀린 지식이 된다.

| 검사 | 구현 | 방식 |
|---|---|---|
| 잘못된 `별칭.컬럼` | `AliasFixRule` (id=24) | 코드가 직접 교정 |
| SELECT 컬럼 순서 | `ColumnOrderRule` (id=25) | 코드가 직접 재배열 |
| 필터 리터럴 변형 | `question_guard.check_literals` | **ReAct 관찰 결과로 피드백** |

리터럴만 피드백 방식인 이유: `'2014-15'` → `'2014-2015'` 로 바꾸는 게 옳아 보여도 모델이
의도적으로 다른 값을 쓴 경우까지 코드가 덮어쓰면 조용한 오답이 된다("모호하면 손대지 않는다").

**`ColumnOrderRule`은 evidence까지 본다.** 질문과 evidence가 다른 순서를 말하면 어느 쪽이
옳은지 판단할 수 없으므로 재배열하지 않는다 — 초판은 질문만 보고 재배열해 seq 450에서
정답이던 순서를 깨뜨렸다.

### 남은 검증 (미구현)

| | 검증 | 대조 대상 | 비고 |
|---|---|---|---|
| **컬럼 존재** | `t1.foo`의 foo가 그 테이블에 있는가 | 스키마 캐시 | `_bind_catalog`는 **테이블만** 본다 |
| 리터럴 값 존재 | 질문에 없는 값이 데이터에 있는가 | 살아있는 데이터 | `EXISTS` 1회. 0건 매칭이면 경고 |

컬럼 존재 검증이 없어서 `column t1.charternum does not exist`가 검증을 통과해 실행 단계에서야
터진다. `AliasFixRule`은 "별칭만 틀린" 경우를 사후 교정할 뿐, 아예 없는 컬럼명은 아무도 안 잡는다.

### ⚠️ 측정 방법론 (다른 모든 작업의 전제)

**n=30에서 ±1~2 차이는 노이즈다.** 30문항 중 12문항이 run마다 뒤집힌다
(`docs/eval-history.md` 참고). 따라서:

- 규칙 검증은 **에러 유형별 건수**로 한다 — 결정론적이고 즉시 판정된다
- EX로 판단하려면 **반복 실행 평균**이나 **문항 수 확대**(데이터셋은 500문항인데
  `california_schools` 30문항만 쓰고 있다)가 필요하다

### P0. thinking 효과 분리 측정 (완료 — 위 참고)

**필요한 run**: thinking OFF + NULLS 규칙 ON (약 40분).
run 100과 비교하면 thinking 기여분이 단독으로 나온다.

이것이 최우선인 이유: thinking이 해롭다면 ReAct 단계를 끄는 것만으로 EX가 오르고
**평가 시간도 절반**이 된다. 이후 모든 실험의 기준선이 바뀌므로 다른 작업보다 먼저
확정해야 한다.

### P1. run 101로 NULLS 규칙 기여분 확정

run 100 vs 101은 규칙 하나만 다르다. 차이가 3건 미만이면 노이즈로 보고, 규칙은
"EX 기여는 없지만 NULL 정렬 오류 자체는 확실히 막는 정확성 보험"으로 유지한다.

> n=30에서 1~2건 차이는 노이즈다. `temperature=0`이어도 vLLM은 완전히 결정론적이지
> 않고, ReAct는 여러 턴을 돌아 분산이 더 크다.

### P2. 등가 컬럼 탐지 프로토타입 (읽기 전용, 등록 없음)

FK 두 쌍을 앵커로 삼아 비키 컬럼을 비교한다. 관계는 세 종류다:

| 종류 | 예 | 탐지 방법 |
|---|---|---|
| **A. 동일 값 복제** | `school` ≡ `School Name` | 조인 후 값 일치율 |
| **B. 코드 ↔ 설명** | `soc` ↔ `School Type` | 함수적 종속(코드 1개 → 설명 1개) |
| C. 조인 키 | `cdscode` | FK 메타데이터 — **이미 있음** |

B가 중요하다: 값 비교로는 일치율 0%라 A 방식으로는 못 잡는데, 지금 glossary에 손으로
채워 넣고 있는 DOC/SOC/EdOpsCode 정의가 전부 이 유형이다. 자동화 이득이 A보다 클 수 있다.

**후보 좁히기** (전부 카탈로그·통계에서 공짜):
타입 호환 / 이름 **토큰** 겹침(전체 문자열 유사도는 오탐만 냈다) / `n_distinct` 근접 /
NULL 비율 근접 / 인덱스 유무(우선순위 신호로만).

**주의**: PK·FK·인덱스 컬럼으로 범위를 좁히면 안 된다. 그건 이미 아는 조인 키이고,
실제 실패를 일으킨 것은 전부 비키 컬럼이다.

### P3. 불일치 분류 — glossary와 정합성 리포트로 분리

일치율만 보지 말고 불일치를 세 갈래로 나눈다(같은 쿼리에서 한 번에 집계 가능):

| 패턴 | 판정 | 대응 |
|---|---|---|
| 한쪽만 NULL | 커버리지 격차 | LEFT JOIN 판단에 영향 |
| 공백·대소문자만 다름 | 표기 불일치 | **cleansing 대상**, 등가로 인정하되 정규화 명시 |
| 둘 다 비NULL인데 값이 다름 | **정합성 위반** | 등가 등록 금지. 정본을 지정해야 함 |

산출물을 둘로 나눈다:
- **glossary 후보** — 일치율 100% + 표기만 다른 것
- **정합성 리포트** — 값 불일치 쌍 + 불일치 행 샘플

세 번째 패턴을 "같은 개념이니 아무거나 쓰라"고 모델에 알려주면 어느 값이 나오든
무작위가 된다. 정본을 지정하면 그 정보 자체가 glossary에 들어갈 가치가 있다.

**부수 가치**: FK로 연결된 비정규화 사본 간 드리프트는 어느 조직에나 있고 보통 아무도
보고 있지 않다. 등가 탐지를 돌리는 것만으로 드러난다 — pgxnl이 text-to-SQL을 넘어
데이터 품질 진단까지 하는 근거가 된다.

### P4. "같은 개념·다른 테이블 오선택" 빈도 측정

P2/P3와 짝이다. 오답 중 이 유형이 몇 %인지 세야 glossary 등록이 정당화된다.
NULLS를 47%로 특정했던 것과 같은 방식.

### P5. glossary 등록 후 재평가

P4 비중이 크면 학교명·카운티·교육구 3건을 등록한다. 형식은 검증된 id=20의 문구를
재사용하고, scope는 **`generation`으로 시작**한다(enrichment 노출은 실측 확인된 것만
최소로 — glossary를 `both`로 넓게 깔았다가 EX가 15/30 → 10/30으로 떨어진 이력이 있다).

`"조인을 추가하지 말고 이미 조인된 테이블의 것을 쓰라"`는 문구를 포함시킬 것 —
규칙 9번 과적합(불필요한 부모 테이블 컬럼 추가)을 다시 유발하지 않기 위해서다.

### P6. 실행 방식 개선 (선택적 적용)

등가 탐지는 **관리자 요청 시에만 실행**한다. 고객 운영 DB에 읽기 부하를 주는 작업이라
등록 시점 전수 조사는 부적절하고, 설계 원칙 1("보조 컴포넌트는 비활성화해도 핵심 흐름이
동작")과도 맞는다.

- `pgxnl/agent/discovery/column_equivalence.py` — 탐지 로직
- `POST /api/targets/{name}/discover/column-equivalence` — 관리자 전용, **후보만 반환**
- 등록은 사람이 승인한 것만 `GlossaryStore.create()`
- `PGXNL_COLUMN_EQUIVALENCE_ENABLED` 기본 `false`, 샘플 행 수·최대 후보 쌍 수 상한

런타임(ReAct 도구) 방식은 권하지 않는다. 루프가 이미 문항당 80초씩 걸리는데 같은 비교를
문항마다 반복하게 된다. 등가 관계는 스키마 속성이므로 한 번 측정해 고정하는 편이 맞다.

### P7. FK 미선언 DB 대응

실제 고객 DB는 성능·운영 편의로 FK를 안 걸어둔 경우가 흔하다. 인덱스 + **값 포함 관계
(inclusion dependency)** 로 미선언 FK를 발견할 수 있다. `discovery/join_history.py`(실행
이력 기반 FK 후보 발견)가 이미 있으므로, 등가 탐지가 **FK 선언이 있으면 그것을, 없으면
발견된 후보를** 쓰도록 두 경로를 다 받게 설계한다.
